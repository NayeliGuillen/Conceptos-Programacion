Módulo 1

Diseño de Esquemas y Normalización

Un dato, un lugar. El arte de no repetir información.

😱 El problema: la tabla "sábana"

Imagina registrar pedidos en UNA sola tabla gigante, repitiendo los datos del cliente en cada fila:

pedidoclienteemail_clienteciudad_clienteproducto
1001Ana Lópezana@mail.comMonterreyLaptop
1002Ana Lópezana@mail.comMonterreyMouse
1003Ana Lópezana@mai.com ⚠️MonterreyTeclado

Los tres males de la duplicación (las anomalías):

✏️ De actualización

Ana cambia de email → hay que corregirlo en TODAS sus filas. Si olvidas una (fila 1003 ☝️), tienes datos contradictorios: ¿cuál email es el bueno?

➕ De inserción

¿Quieres registrar a un cliente nuevo que aún no compra nada? No puedes: la tabla exige un pedido. El cliente "no cabe" sin inventar datos.

🗑️ De borrado

Borras el único pedido de un cliente → ¡perdiste también al cliente! Sus datos vivían solo en esa fila.

La solución: normalizar (1FN → 2FN → 3FN)

La normalización🇪🇸 Normalización / 🇺🇸 Normalization — Proceso de organizar tablas para eliminar redundancia: cada dato vive en UN solo lugar y las tablas se conectan por llaves foráneas. divide la tabla sábana en tablas enfocadas conectadas por llaves foráneas. Las "formas normales" son niveles progresivos de limpieza:

1FN — Primera Forma Normal: celdas atómicas

Cada celda guarda UN solo valor. ❌ telefonos = "811-111, 812-222" (dos teléfonos en una celda) → ✅ una tabla Telefonos con una fila por teléfono. Si necesitas "buscar por el segundo teléfono", la celda con lista te lo impide.

2FN — Segunda Forma Normal: todo depende de la llave COMPLETA

Aplica a llaves compuestas. Si la llave de DetallePedido es (pedido_id, producto_id), la columna nombre_producto solo depende de producto_id (la mitad de la llave) → se muda a la tabla Productos.

3FN — Tercera Forma Normal: nada depende de columnas que no son llave

En Clientes, si guardas ciudad y también estado, el estado depende de la ciudad (Monterrey → Nuevo León), no del cliente → tabla Ciudades aparte. Regla mnemotécnica: "cada columna depende de la llave, de toda la llave y nada más que la llave".

⚖️ Matiz senior — desnormalizar a propósito: normalizar optimiza la ESCRITURA (un dato, un lugar) pero puede encarecer la LECTURA (más JOINs). En sistemas de reportes/analítica se desnormaliza deliberadamente: se duplica el dato para leer más rápido. La regla: normaliza por defecto; desnormaliza solo con una razón medida, y documentándolo.

Módulo 2

SQL Avanzado

JOINs, agregaciones, subconsultas y CTEs — el 90% del SQL profesional.

🤝 Los JOINs, de una vez por todas

Un JOIN🇺🇸 JOIN — Operación que combina filas de dos tablas emparejándolas por una condición (normalmente FK = PK). Los tipos definen qué pasa con las filas SIN pareja. empareja filas de dos tablas. La diferencia entre tipos es qué pasa con las filas que no encuentran pareja:

TipoDevuelveEjemplo mental
INNER JOINSolo filas CON pareja en ambas tablasClientes que SÍ tienen pedidos
LEFT JOINTODAS las de la izquierda + pareja si existe (NULL si no)TODOS los clientes, tengan pedidos o no
RIGHT JOINTODAS las de la derecha (es un LEFT volteado; se usa poco)—
FULL OUTER JOINTodas de ambas, con NULL donde falte parejaAuditorías: ¿qué quedó suelto de cada lado?
 
-- ¿Qué clientes NO han comprado nunca? (truco clásico de entrevista)
SELECT c.nombre
FROM Clientes c
LEFT JOIN Pedidos p ON p.cliente_id = c.id
WHERE p.id IS NULL;   -- los que quedaron sin pareja

📊 Agregaciones: GROUP BY y HAVING

GROUP BY agrupa filas y las funciones de agregación (COUNT, SUM, AVG, MAX, MIN) resumen cada grupo. HAVING filtra grupos (WHERE filtra filas, ANTES de agrupar):

-- Ventas totales por cliente en 2026, solo clientes con más de $10,000
SELECT c.nombre,
       COUNT(p.id)      AS num_pedidos,
       SUM(p.total)     AS total_comprado
FROM Clientes c
INNER JOIN Pedidos p ON p.cliente_id = c.id
WHERE p.fecha >= '2026-01-01'      -- filtra FILAS antes de agrupar
GROUP BY c.nombre
HAVING SUM(p.total) > 10000       -- filtra GRUPOS ya calculados
ORDER BY total_comprado DESC;

🧠 Truco para recordar el orden de evaluación: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY. Por eso WHERE no puede usar el resultado de SUM(): todavía no existe cuando WHERE se ejecuta.

🪆 Subconsultas y CTEs (consultas legibles)

Una subconsulta es una consulta dentro de otra. Una CTE🇺🇸 CTE — Common Table Expression — Consulta nombrada con WITH que actúa como "tabla temporal" dentro de tu query. Hace legibles las consultas complejas y puede encadenarse. (WITH) es lo mismo pero con nombre — como extraer una función en código (¡DRY aplicado a SQL!):

-- CTE: "define primero, usa después" — mucho más legible
WITH ventas_por_cliente AS (
    SELECT cliente_id, SUM(total) AS total_comprado
    FROM Pedidos
    GROUP BY cliente_id
)
SELECT c.nombre, v.total_comprado
FROM ventas_por_cliente v
INNER JOIN Clientes c ON c.id = v.cliente_id
WHERE v.total_comprado > (
    SELECT AVG(total) FROM Pedidos   -- subconsulta: el promedio general
);   -- clientes que compran arriba del promedio
🐘 PostgreSQL vs 🐬 MySQL: ambos son excelentes y gratuitos. PostgreSQL destaca en features avanzados (JSON nativo potente, window functions completas, tipos ricos) y rigor; MySQL en sencillez y ubicuidad (WordPress, hosting barato). El SQL de esta guía funciona en los dos.
🪟 Siguiente nivel — window functions: ROW_NUMBER() OVER (PARTITION BY ...) numera/acumula SIN colapsar filas como GROUP BY. Típica de entrevista avanzada: "dame el pedido más reciente DE CADA cliente".

Módulo 3

Índices y Optimización de Queries

La diferencia entre 20 milisegundos y 20 segundos.

📖 El índice del libro

Buscar "polimorfismo" en un libro de 800 páginas: ¿lees página por página (un full table scan🇺🇸 Full Table Scan — La base de datos lee TODAS las filas de la tabla para responder la consulta. Con millones de filas es la causa #1 de consultas lentas.) o vas al índice alfabético del final, que te dice "página 214"? Un índice🇪🇸 Índice / 🇺🇸 Index — Estructura ordenada (típicamente un árbol B-tree) que la base de datos mantiene sobre una o más columnas para localizar filas sin leer toda la tabla. Acelera lecturas; encarece escrituras. de base de datos es exactamente eso: una estructura ordenada (un árbol B-tree) que apunta directo a las filas. Es el O(log n) de CP4 aplicado: en una tabla de 10 millones de filas, ~23 saltos en vez de 10 millones de lecturas.

-- Sin índice: esta consulta lee TODA la tabla (lenta con millones de filas)
SELECT * FROM Pedidos WHERE cliente_id = 7;

-- Crear el índice: la BD mantiene un "índice de libro" sobre esa columna
CREATE INDEX idx_pedidos_cliente ON Pedidos (cliente_id);

-- La MISMA consulta ahora es casi instantánea 🚀

-- ¿Cómo saber qué está haciendo la BD? Pídele su plan:
EXPLAIN SELECT * FROM Pedidos WHERE cliente_id = 7;
-- "Seq Scan" (escaneo completo) = mal 😬 · "Index Scan" = bien ✅

Las llaves primarias ya traen índice automático. Los candidatos naturales a indexar: llaves foráneas y columnas que aparecen mucho en WHERE, JOIN y ORDER BY.

El costo oculto y las reglas del juego

⚖️ Los índices no son gratis

  • 💾 Ocupan espacio (a veces tanto como la tabla).
  • 🐢 Encarecen las escrituras: cada INSERT/UPDATE también actualiza cada índice. Una tabla con 12 índices escribe lento.
  • 🧭 Regla: indexa lo que se CONSULTA mucho; no indexes "por si acaso". Tablas de mucha escritura y poca lectura → pocos índices.

🎯 Índices compuestos: el orden importa

Un índice sobre (cliente_id, fecha) es como un directorio ordenado por apellido Y LUEGO nombre:

  • ✅ Sirve para buscar por cliente_id solo
  • ✅ Sirve para cliente_id + fecha
  • ❌ NO sirve para buscar por fecha sola (¿buscarías "todos los Juan" en un directorio ordenado por apellido?)
🕵️ Checklist senior cuando una consulta es lenta: 1) Corre EXPLAIN y busca escaneos completos. 2) ¿La columna del WHERE/JOIN tiene índice? 3) ¿Estás haciendo SELECT * cuando solo necesitas 3 columnas? 4) ¿Envuelves la columna indexada en una función? (WHERE YEAR(fecha)=2026 anula el índice; usa rangos: fecha >= '2026-01-01' AND fecha < '2027-01-01'). 5) ¿Traes un millón de filas sin paginar?

Módulo 4

Transacciones y Consistencia

Todo o nada: por qué el dinero nunca desaparece "a medias".

💸 El ejemplo eterno: la transferencia bancaria

Transferir $500 de Ana a Luis son DOS operaciones: restar a Ana y sumar a Luis. ¿Qué pasa si el servidor se apaga entre las dos? Sin protección: los $500 se esfumaron. Una transacción🇪🇸 Transacción / 🇺🇸 Transaction — Grupo de operaciones que se ejecutan como una unidad indivisible: o TODAS se aplican (COMMIT) o NINGUNA (ROLLBACK). agrupa operaciones en una unidad todo-o-nada:

BEGIN TRANSACTION;                -- abre la "burbuja protegida"

UPDATE Cuentas SET saldo = saldo - 500 WHERE titular = 'Ana';
UPDATE Cuentas SET saldo = saldo + 500 WHERE titular = 'Luis';

COMMIT;      -- ✅ TODO se aplica de golpe y queda permanente
-- Si algo falla en medio (error, apagón):
ROLLBACK;    -- ❌ NADA se aplica: como si nunca hubiera pasado

Las 4 garantías: ACID

A — Atomicidad

Todo o nada. No existen las transferencias "a medias".

C — Consistencia

La BD pasa de un estado válido a otro válido: las reglas (saldos no negativos, FKs) se respetan siempre.

I — Aislamiento (Isolation)

Transacciones simultáneas no se ven "a medio hacer" entre sí.

D — Durabilidad

Tras el COMMIT, el cambio sobrevive apagones: ya está en disco.

Aislamiento: qué tan "solas" van las transacciones

Si dos transacciones tocan los mismos datos a la vez, pueden verse cosas raras. Los niveles de aislamiento son el "volumen" de protección — más protección, menos concurrencia:

  • Read Uncommitted — puedes leer cambios NO confirmados de otros (lecturas sucias). Casi nunca se usa.
  • Read Committed — solo lees lo confirmado. Default en PostgreSQL y SQL Server.
  • Repeatable Read — lo que lees no cambia durante tu transacción. Default en MySQL/InnoDB.
  • Serializable — como si las transacciones corrieran una por una. Máxima seguridad, mínimo paralelismo.

🔒 Bloqueos y deadlocks

Para aislarse, la BD usa bloqueos (locks): "esta fila es mía hasta que termine". El riesgo famoso: el deadlock🇺🇸 Deadlock / 🇪🇸 Abrazo mortal — Dos transacciones se esperan mutuamente por bloqueos cruzados y ninguna puede avanzar. La BD detecta y mata a una de las dos. — la transacción A bloquea la fila 1 y espera la 2; la B bloquea la 2 y espera la 1. Ninguna avanza; la BD mata a una.

Prevención práctica: transacciones CORTAS (no metas llamadas a APIs dentro de una transacción), y toca las tablas siempre en el mismo orden.

🌉 Conexión con lo que ya sabes: ¿recuerdas la advertencia de CP4 sobre UPDATE sin WHERE? La versión profesional: haz cambios masivos DENTRO de una transacción → verifica el número de filas afectadas → COMMIT si es lo esperado, ROLLBACK si no. Red de seguridad instantánea.

Módulo 5

NoSQL a Fondo

MongoDB, Redis y DynamoDB: cada una brilla en lo suyo.

🍃 MongoDB — documentos flexibles

Guarda documentos tipo JSON en colecciones. Cada documento puede tener campos distintos — no hay esquema rígido. Ideal cuando la estructura varía (catálogos con atributos diferentes por producto) o evoluciona rápido:

// Un documento en la colección "productos" — todo junto, sin JOINs
{
  "_id": "prod_42",
  "nombre": "Laptop Dell XPS",
  "precio": 24999.90,
  "specs": { "ram": "16GB", "cpu": "i7" },     // anidado
  "reseñas": [                                    // ¡lista adentro!
    { "usuario": "ana", "estrellas": 5 }
  ]
}

// Consultar: parecido a un diccionario, no a SQL
db.productos.find({ "precio": { "$lt": 30000 } })   // $lt = less than

⚖️ El trade-off: lo que en SQL normalizabas en 4 tablas aquí vive junto (lectura rapidísima de UN producto completo), pero consultas relacionales complejas ("clientes que compraron X y también Y") son más torpes. La flexibilidad también significa que NADA te obliga a la consistencia del esquema: la disciplina queda en tu código.

⚡ Redis — el rayo en memoria

Base clave-valor EN MEMORIA RAM: lecturas/escrituras en microsegundos. Ya la viste como caché en CP5; también es el estándar para:

  • • Sesiones de usuario y contadores de rate limiting
  • • Rankings en vivo (sorted sets) y colas ligeras
  • • Pub/sub para tiempo real entre servidores

RAM = rápida pero volátil y cara: Redis complementa a tu base principal, no la reemplaza.

♾️ DynamoDB — escala sin límites (AWS)

Clave-valor/documentos administrada por AWS: escala a millones de operaciones por segundo con latencia constante de milisegundos, sin servidores que operar.

  • • Carritos de compra, perfiles, sesiones a escala masiva
  • • Pagas por lectura/escritura, no por servidor
  • • El precio: DEBES diseñar las tablas alrededor de tus patrones de acceso — las consultas "creativas" posteriores son difíciles

La tabla de decisión definitiva

Tu situaciónUsaPorque...
Datos de negocio con relaciones (ventas, usuarios, inventario)PostgreSQL / MySQL / SQL ServerIntegridad, transacciones ACID, consultas flexibles
Documentos de estructura variable que se leen completosMongoDBEsquema flexible, el documento viaja entero
Caché, sesiones, contadores, tiempo realRedisMicrosegundos, estructuras especializadas en RAM
Escala masiva con patrones de acceso conocidos y fijosDynamoDBEscala infinita administrada, latencia constante
🧠 La respuesta senior a "¿SQL o NoSQL?": "Sí." Los sistemas reales usan persistencia políglota: PostgreSQL para el negocio + Redis para caché/sesiones + quizá Mongo para un catálogo flexible. La pregunta correcta nunca es cuál es "mejor", sino cuál encaja con ESTE dato y ESTE patrón de acceso.

Módulo 6

ORMs

Objetos ↔ tablas sin escribir (casi) SQL... y sus trampas.

🌉 El traductor entre dos mundos

Tu código piensa en objetos (CP2); la base piensa en tablas. Un ORM🇺🇸 ORM — Object-Relational Mapper — Librería que mapea clases ↔ tablas y objetos ↔ filas, generando el SQL automáticamente. Ej: Entity Framework (C#), SQLAlchemy (Python), Prisma (JS/TS). (Object-Relational Mapper) traduce automáticamente: defines clases, y él genera las tablas y el SQL. Los grandes por ecosistema: Entity Framework Core (C#), SQLAlchemy / Django ORM (Python), y en el mundo JavaScript/TypeScript: Prisma, TypeORM y Sequelize.

# 1. La clase ES la tabla (modelo declarativo)
class Producto(Base):
    __tablename__ = "productos"
    id     = Column(Integer, primary_key=True)
    nombre = Column(String(100))
    precio = Column(Numeric(10, 2))

# 2. Consultas en Python — el ORM genera el SQL:
baratos = (session.query(Producto)
           .filter(Producto.precio < 30000)
           .order_by(Producto.precio)
           .all())
# → SELECT * FROM productos WHERE precio < 30000 ORDER BY precio

# 3. Crear = instanciar y guardar (CP2 en acción)
nuevo = Producto(nombre="Mouse", precio=499)
session.add(nuevo)
session.commit()     # ¡transacción incluida!
// 1. La clase ES la tabla (EF Core la mapea por convención)
public class Producto
{
    public int Id { get; set; }         // → llave primaria automática
    public string Nombre { get; set; }
    public decimal Precio { get; set; }
}

// 2. Consultas con LINQ — EF genera el SQL:
var baratos = await db.Productos
    .Where(p => p.Precio < 30000)
    .OrderBy(p => p.Precio)
    .ToListAsync();
// → SELECT * FROM Productos WHERE Precio < 30000 ORDER BY Precio

// 3. Crear = instanciar y guardar (CP2 en acción)
db.Productos.Add(new Producto { Nombre = "Mouse", Precio = 499 });
await db.SaveChangesAsync();   // ¡transacción incluida!

🪤 La trampa clásica: el problema N+1

El error de rendimiento #1 con ORMs. Quieres mostrar 100 pedidos con el nombre de su cliente:

# ❌ N+1: parece inocente, pero...
pedidos = session.query(Pedido).all()          # 1 consulta
for p in pedidos:
    print(p.cliente.nombre)   # ¡una consulta MÁS por CADA pedido! (lazy loading)
# Total: 1 + 100 = 101 consultas 🐌

# ✅ Eager loading: dile al ORM que traiga la relación de una vez
pedidos = (session.query(Pedido)
           .options(joinedload(Pedido.cliente))   # SQLAlchemy
           .all())
# En EF Core: db.Pedidos.Include(p => p.Cliente)
# Total: 1 consulta con JOIN 🚀

La causa: el lazy loading (carga perezosa) trae las relaciones "hasta que las tocas" — cómodo, pero dentro de un bucle es una consulta por vuelta. La app va "bien" con 10 registros de prueba y muere con 10,000 reales.

📦 Migraciones: Git para tu esquema

Las migraciones🇺🇸 Migrations — Archivos versionados que describen cada cambio del esquema (crear tabla, agregar columna). Se aplican en orden y mantienen todas las copias de la BD sincronizadas. versionan los cambios del esquema: "agregar columna telefono" queda en un archivo que se aplica en dev, staging y producción en orden. Herramientas: Alembic (SQLAlchemy), dotnet ef migrations (EF Core), prisma migrate. Nunca cambies el esquema de producción "a mano".

⚖️ ¿ORM o SQL a mano? (pregunta de entrevista)

ORM para el 90%: CRUD, consultas típicas — productividad, seguridad (parametriza contra inyección SQL) y migraciones.

SQL directo para el 10%: reportes complejos, optimizaciones finas, operaciones masivas. Todos los ORMs te dejan "bajar" a SQL crudo cuando hace falta. Un senior domina AMBOS y sabe cuándo cambiar.
