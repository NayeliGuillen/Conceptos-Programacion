Módulo 1

MVC y Arquitectura en Capas

Separar responsabilidades para que 50 personas puedan trabajar en el mismo código sin volverse locas.

🎭 ¿Qué es MVC?

MVC🇺🇸 MVC — Model-View-Controller — Patrón arquitectónico que separa la aplicación en tres partes: Modelo (datos y reglas de negocio), Vista (presentación) y Controlador (coordinador que recibe las peticiones). (Modelo-Vista-Controlador) es un patrón arquitectónico: una forma de repartir el trabajo de una aplicación en tres papeles claros. Volvamos al restaurante de CP3, ahora viendo la organización interna:

📊 Modelo (Model) = la cocina y la despensa

Los datos y las reglas de negocio: las clases (CP2), las validaciones, el acceso a la base de datos. No sabe NADA de pantallas ni de HTTP. Aquí vive la clase CuentaBancaria con su regla de "no retirar más del saldo".

🖼️ Vista (View) = el plato servido

La presentación: el HTML que ve el usuario, o el JSON que devuelve la API. Solo muestra datos; no calcula ni decide nada. Si mañana cambias el diseño, solo tocas la vista.

🎛️ Controlador (Controller) = el mesero coordinador

Recibe la petición HTTP, decide a qué modelo llamar, y elige qué vista devolver. Es delgado: coordina, no contiene lógica de negocio.

Petición HTTP → CONTROLADOR → llama al MODELO (lógica + datos) → resultado → VISTA (HTML/JSON) → Respuesta

MVC en código real

# ===== MODELO: datos y reglas de negocio =====
class Producto:
    def __init__(self, id, nombre, precio):
        self.id, self.nombre, self.precio = id, nombre, precio

    @staticmethod
    def buscar_por_id(id):
        # aquí iría la consulta a la base de datos
        return Producto(id, "Laptop", 24999.90)

# ===== CONTROLADOR: coordina, no calcula =====
@app.route("/productos/<int:id>")
def detalle_producto(id):
    producto = Producto.buscar_por_id(id)   # 1. pide al MODELO
    return render_template("detalle.html", p=producto)  # 2. elige la VISTA

# ===== VISTA: detalle.html — solo presenta =====
# <h1>{{ p.nombre }}</h1> <p>${{ p.precio }}</p>
// ===== MODELO: datos y reglas de negocio =====
public class Producto
{
    public int Id { get; set; }
    public string Nombre { get; set; }
    public decimal Precio { get; set; }
}

// ===== CONTROLADOR: coordina, no calcula =====
public class ProductosController : Controller
{
    public IActionResult Detalle(int id)
    {
        var producto = _repositorio.BuscarPorId(id);  // 1. pide al MODELO
        return View(producto);                        // 2. elige la VISTA
    }
}

// ===== VISTA: Detalle.cshtml — solo presenta =====
// <h1>@Model.Nombre</h1> <p>$@Model.Precio</p>

Más allá de MVC: la arquitectura en capas

En proyectos grandes, el backend se organiza en capas donde cada una solo habla con la de abajo:

1. Capa de Presentación — controladores y vistas/API. Recibe HTTP, devuelve respuestas.
2. Capa de Negocio (Services) — las reglas: "un cliente moroso no puede comprar". El corazón de la app.
3. Capa de Datos (Repositories) — el único lugar que habla con la base de datos.

¿Por qué molestarse en separar?

  • ✅ Cambios aislados: cambiar de SQL Server a PostgreSQL solo toca la capa de datos.
  • ✅ Pruebas fáciles: pruebas la lógica de negocio sin levantar base de datos ni servidor web (¿recuerdas las unitarias de CP4?).
  • ✅ Equipos en paralelo: frontend y backend avanzan sin bloquearse.
  • 📖 Primos de MVC que escucharás: MVVM (apps de escritorio/móviles, ej. WPF), MVP, y "Clean Architecture" — todos persiguen lo mismo: separar responsabilidades.

Patrones de Diseño a Fondo

De la teoría de CP2 al código que verás en proyectos reales.

🗂️ Las 3 familias de patrones (Gang of Four)

El libro "Design Patterns" (1994) catalogó 23 patrones en 3 familias. No necesitas memorizarlos todos: necesitas ubicar las familias y dominar los 4-5 que aparecen a diario:

🏗️ Creacionales

CÓMO se crean los objetos: Singleton, Factory, Builder. Resuelven "quién y cuándo hace el new".

🧩 Estructurales

CÓMO se componen las clases entre sí: Adapter, Decorator, Facade. Resuelven "cómo conecto piezas que no encajan".

🤝 De comportamiento

CÓMO colaboran y se comunican: Observer, Strategy, Command. Resuelven "quién decide qué y quién avisa a quién".

🔒 Singleton — una sola instancia global

Problema que resuelve: hay cosas que DEBEN existir una sola vez: la configuración de la app, el pool de conexiones. Analogía: solo hay UN director en la escuela; todos consultan al mismo.

class Configuracion:
    _instancia = None                 # la única instancia vive aquí

    def __new__(cls):
        if cls._instancia is None:    # ¿ya existe? si no, créala
            cls._instancia = super().__new__(cls)
            cls._instancia.tema = "oscuro"
        return cls._instancia         # siempre devuelve LA MISMA

a = Configuracion()
b = Configuracion()
print(a is b)    # True → son el MISMO objeto
public sealed class Configuracion
{
    // la única instancia, creada una sola vez (thread-safe con Lazy)
    private static readonly Lazy<Configuracion> _instancia =
        new(() => new Configuracion());

    public static Configuracion Instancia => _instancia.Value;

    public string Tema { get; set; } = "oscuro";

    private Configuracion() { }   // constructor PRIVADO: nadie más hace new
}

var a = Configuracion.Instancia;
var b = Configuracion.Instancia;
Console.WriteLine(ReferenceEquals(a, b));  // True → el MISMO objeto

⚠️ Advertencia senior: el Singleton está semi "mal visto" cuando se abusa: crea estado global escondido y dificulta las pruebas. En frameworks modernos se prefiere registrarlo en el contenedor de inyección de dependencias con tiempo de vida singleton (ASP.NET: AddSingleton).

🏭 Factory — la fábrica decide qué construir

Problema que resuelve: el código cliente no debería decidir qué clase concreta crear (eso lo acopla a todas). Analogía: pides "un platillo del día"; la cocina decide cuál preparar.

def crear_notificador(preferencia):   # LA FÁBRICA
    if preferencia == "email":
        return NotificadorEmail()
    if preferencia == "sms":
        return NotificadorSMS()
    return NotificadorPush()          # default

# El cliente NO sabe qué clase concreta recibió — ni le importa:

notificador.enviar("Tu pedido llegó")
# Agregar WhatsApp mañana = tocar SOLO la fábrica (Open/Closed ✔)
public static class NotificadorFactory   // LA FÁBRICA
{
    public static INotificador Crear(string preferencia) =>
        preferencia switch
        {
            "email" => new NotificadorEmail(),
            "sms"   => new NotificadorSMS(),
            _        => new NotificadorPush()   // default
        };
}

// El cliente NO sabe qué clase concreta recibió — ni le importa:
var notificador = NotificadorFactory.Crear(usuario.Preferencia);
notificador.Enviar("Tu pedido llegó");

👀 Observer — suscribirse y ser notificado

Problema que resuelve: cuando algo cambia, varios interesados deben enterarse — sin que el emisor los conozca uno por uno. Analogía: el canal de YouTube no llama a cada suscriptor: publica, y la campanita avisa a todos.

class Pedido:                        # el OBSERVADO (sujeto)
    def __init__(self):
        self._suscriptores = []

    def suscribir(self, funcion):
        self._suscriptores.append(funcion)

    def marcar_enviado(self):
        for avisar in self._suscriptores:   # notifica a TODOS
            avisar("¡Pedido enviado!")

pedido = Pedido()
pedido.suscribir(lambda msg: print(f"📧 Email: {msg}"))
pedido.suscribir(lambda msg: print(f"📱 App: {msg}"))
pedido.marcar_enviado()   # ambos se enteran automáticamente
public class Pedido                   // el OBSERVADO (sujeto)
{
    // C# tiene el patrón INTEGRADO en el lenguaje: los eventos
    public event Action<string> Enviado;

    public void MarcarEnviado()
        => Enviado?.Invoke("¡Pedido enviado!");  // notifica a TODOS
}

var pedido = new Pedido();
pedido.Enviado += msg => Console.WriteLine($"📧 Email: {msg}");
pedido.Enviado += msg => Console.WriteLine($"📱 App: {msg}");
pedido.MarcarEnviado();   // ambos se enteran automáticamente

Dos patrones más que verás a diario

♟️ Strategy — algoritmos intercambiables

Defines una familia de algoritmos tras una interfaz y los cambias en tiempo de ejecución: calcular envío por Estafeta, DHL o FedEx; cobrar con tarjeta, PayPal o transferencia.

Analogía: distintas rutas en Waze para el mismo destino — eliges la estrategia según el tráfico. Es polimorfismo (CP2) aplicado con intención.

🗃️ Repository — la puerta única a los datos

Una clase por entidad (ProductoRepository) concentra TODO el acceso a datos: buscar_por_id(), guardar(). El resto de la app no sabe si detrás hay SQL, Mongo o un archivo.

Es la "capa de datos" del módulo 1 hecha patrón. Facilita cambiar de base de datos y hacer pruebas con repositorios falsos (mocks).

Módulo 3

Procesos Asíncronos

Deja de esperar parado: async/await y concurrencia.

☕ La analogía de la cafetería

Código síncrono: el barista toma tu orden, prepara TU café mientras la fila espera congelada, te lo entrega, y solo entonces atiende al siguiente. Código asíncrono🇪🇸 Asíncrono / 🇺🇸 Asynchronous — Modelo donde el programa inicia una operación lenta (red, disco) y sigue haciendo otras cosas mientras espera el resultado, en lugar de bloquearse.: toma tu orden, pone la máquina a trabajar, y MIENTRAS el café sale, atiende a los siguientes clientes. Cuando tu café está listo, te llama por tu nombre.

En backend esto es vital: cuando tu API espera una respuesta de la base de datos o de otra API (operaciones de I/O que tardan milisegundos eternos), el hilo NO debe quedarse bloqueado — debe atender otras peticiones. Así un mismo servidor atiende miles de usuarios simultáneos.

import asyncio
import httpx    # cliente HTTP asíncrono (pip install httpx)

# async def = "esta función puede pausarse mientras espera"
async def obtener_usuario(id):
    async with httpx.AsyncClient() as http:
        # await = "pausa AQUÍ y atiende otras cosas mientras llega"
        r = await http.get(f"https://api.ejemplo.com/users/{id}")
        return r.json()

async def main():
    # 3 peticiones AL MISMO TIEMPO, no una tras otra:
    usuarios = await asyncio.gather(
        obtener_usuario(1), obtener_usuario(2), obtener_usuario(3)
    )
    # si cada una tarda 1 seg: total ≈ 1 seg, no 3 🚀

asyncio.run(main())
// async Task = "este método puede pausarse mientras espera"
async Task<Usuario> ObtenerUsuario(int id)
{
    // await = "pausa AQUÍ y libera el hilo para otras peticiones"
    var r = await _http.GetAsync($"https://api.ejemplo.com/users/{id}");
    return await r.Content.ReadFromJsonAsync<Usuario>();
}

// 3 peticiones AL MISMO TIEMPO, no una tras otra:
var tareas = new[] { ObtenerUsuario(1), ObtenerUsuario(2), ObtenerUsuario(3) };
Usuario[] usuarios = await Task.WhenAll(tareas);
// si cada una tarda 1 seg: total ≈ 1 seg, no 3 🚀

Los conceptos que no debes confundir

Asincronía

UN trabajador que no espera parado: mientras el horno hornea, lava trastes. Ideal para I/O (red, disco, base de datos).

Concurrencia / Hilos

VARIOS trabajadores turnándose o en paralelo. Los hilos🇺🇸 Thread / 🇪🇸 Hilo — Unidad de ejecución dentro de un proceso. Varios hilos comparten memoria, lo que permite paralelismo pero exige cuidado con las condiciones de carrera. comparten memoria — cuidado con dos hilos tocando la misma variable (condición de carrera).

Paralelismo

Varios trabajos ejecutándose LITERALMENTE al mismo tiempo en varios núcleos del CPU. Ideal para cálculo pesado (procesar imágenes, cifrar).

🧭 Regla de decisión senior: ¿tu código pasa el tiempo ESPERANDO (red, disco, BD)? → async/await. ¿Pasa el tiempo CALCULANDO (CPU al 100%)? → paralelismo/multiproceso. Usar async para cálculo pesado no ayuda en nada — el CPU sigue igual de ocupado.

Módulo 4

Colas de Mensajes

El usuario no debe esperar por trabajo que puede hacerse "al ratito".

🌮 La analogía de la taquería con comanda

Sin cola: pides 5 tacos y el taquero no atiende a NADIE más hasta terminar los tuyos. Con cola de mensajes🇪🇸 Cola de Mensajes / 🇺🇸 Message Queue — Buzón intermedio donde los productores depositan trabajos y los consumidores (workers) los procesan a su ritmo. Desacopla y absorbe picos de carga.: el mesero anota tu orden en la comanda (la cola), te da tu número, y los taqueros (los workers🇺🇸 Worker — Proceso consumidor que toma trabajos de una cola y los ejecuta en segundo plano, independiente de la petición web original.) van despachando órdenes a su ritmo. Nadie se bloquea, y si llega un camión de turistas, las órdenes solo esperan un poco más — el sistema no colapsa.

PRODUCTOR (tu API) → 📥 COLA (RabbitMQ/Kafka/SQS) → CONSUMIDORES (workers en segundo plano)

El ejemplo clásico: el usuario se registra. ¿Debe esperar 4 segundos mientras envías el correo de bienvenida, generas su avatar y lo das de alta en el CRM? No: guardas el usuario (rápido), encolas 3 mensajes, respondes "¡listo!" en 200ms... y los workers hacen el resto tras bambalinas.

¿Cuándo usar una cola? Las 3 señales

⏳ Trabajo lento no urgente

Enviar correos, generar PDFs, procesar videos, redimensionar imágenes. El usuario no necesita verlo terminado YA.

🌊 Picos de tráfico

El Buen Fin llegan 10,000 pedidos por minuto pero tu sistema procesa 1,000. La cola absorbe el pico: encola rápido, procesa a tu ritmo. Sin cola: se cae.

🔌 Desacoplar sistemas

El sistema de facturación está en mantenimiento; los mensajes lo esperan en la cola. Ningún pedido se pierde. Los sistemas ya no dependen de que el otro esté vivo.

Las herramientas que escucharás

HerramientaIdea centralTípico para...

🎯 Concepto de entrevista — idempotencia: las colas suelen garantizar entrega "al menos una vez" (at-least-once), lo que significa que un mensaje puede llegar DUPLICADO. Tu worker debe ser idempotente: procesar el mismo mensaje dos veces no debe causar daño (no cobrar dos veces, no enviar dos correos). Truco típico: registrar el id del mensaje procesado y descartar repetidos.

WebSockets y Tiempo Real

Cuando "recarga la página" no es aceptable.

📞 De cartas a llamada telefónica

HTTP (CP3) es como enviar cartas: pides, te responden, fin de la conversación. Perfecto para páginas y APIs... pero fatal para un chat: ¿le mandas una carta al servidor cada segundo preguntando "¿ya me escribieron?"? Un WebSocket🇺🇸 WebSocket — Protocolo (ws:// o wss://) que abre una conexión PERMANENTE y bidireccional entre cliente y servidor: ambos pueden enviarse mensajes en cualquier momento, sin nuevas peticiones. es una llamada telefónica: la línea queda abierta y AMBOS lados hablan cuando quieran, al instante.

Un mini-servidor de chat

import asyncio, websockets   # pip install websockets

conectados = set()

async def chat(websocket):
    conectados.add(websocket)          # nuevo usuario en línea
    try:
        async for mensaje in websocket:  # cada mensaje que envía...
            for usuario in conectados:   # ...se reenvía a TODOS
                await usuario.send(mensaje)
    finally:
        conectados.remove(websocket)    # se desconectó

async def main():
    async with websockets.serve(chat, "localhost", 8765):
        await asyncio.Future()   # correr para siempre

asyncio.run(main())   # clientes se conectan a ws://localhost:8765
// SignalR: la librería de tiempo real de ASP.NET Core.
// Abstrae WebSockets (con fallback automático a SSE/polling).

public class ChatHub : Hub
{
    // el cliente llama a este método...
    public async Task EnviarMensaje(string usuario, string texto)
    {
        // ...y el hub lo retransmite a TODOS los conectados
        await Clients.All.SendAsync("RecibirMensaje", usuario, texto);
    }
}

// En Program.cs:
builder.Services.AddSignalR();
app.MapHub<ChatHub>("/chat");
// clientes JS/C# se suscriben a "RecibirMensaje" y reciben al instante

🧠 Lo que cambia al pensar en tiempo real

  • 🔌 Estado por conexión: el servidor ahora "recuerda" quién está conectado (adiós stateless puro de REST).
  • 📉 Reconexión: las conexiones se caen (wifi, túneles). El cliente debe reconectar y recuperar lo perdido.
  • ⚖️ Escalar es más difícil: con varios servidores, ¿cómo le avisa el servidor A a un usuario conectado al B? Respuesta típica: un canal compartido con Redis pub/sub (módulo 6).

🧭 Regla de decisión

¿De verdad necesitas tiempo real? Sé honesta:

• Dashboard que se actualiza cada minuto → polling basta.

• Notificaciones del servidor al usuario → SSE.

• Chat, colaboración, juegos (ida y vuelta instantánea) → WebSocket. Cada nivel agrega complejidad: usa el más simple que resuelva el problema.

Módulo 6

Rate Limiting, Caching y Rendimiento

No calcules dos veces lo que ya sabes; no dejes que uno acapare todo.

🧠 Caching: la memoria de corto plazo

Un caché🇺🇸 Cache / 🇪🇸 Caché — Almacén temporal de resultados ya calculados o consultados, mucho más rápido que recalcularlos o volver a pedirlos. Se invalida o expira (TTL) para no servir datos viejos. guarda resultados que ya calculaste para no repetir el trabajo. Analogía: te preguntan la hora; ves tu reloj. Te la vuelven a preguntar 10 segundos después: NO vuelves a ver el reloj — la recuerdas. Eso es un caché, con el riesgo obvio: si pasan 10 minutos, tu "hora recordada" ya es mentira. Por eso todo caché tiene expiración (TTL).

Navegador
imágenes, CSS, JS que no re-descarga
🗺️
CDN
copias de tu contenido cerca del usuario (Cloudflare)
⚡
Aplicación

Base de datos
la BD también cachea sus consultas repetidas
import redis, json
cache = redis.Redis()

# Patrón CACHE-ASIDE: el más común del mundo
def obtener_producto(id):
    en_cache = cache.get(f"producto:{id}")
    if en_cache:                         # 1. ¿está en caché? (HIT)
        return json.loads(en_cache)      #    devuélvelo en ~1ms 🚀

    producto = consultar_base_de_datos(id)  # 2. no está (MISS): a la BD (~50ms)
    cache.setex(f"producto:{id}", 300,      # 3. guárdalo con TTL de 300 seg
                json.dumps(producto))
    return producto
// Patrón CACHE-ASIDE con la caché en memoria de ASP.NET Core
public class ProductoService
{
    private readonly IMemoryCache _cache;

    public async Task<Producto> ObtenerProducto(int id)
    {
        return await _cache.GetOrCreateAsync($"producto:{id}", async entry =>
        {
            // solo se ejecuta si NO está en caché (MISS)
            entry.AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(5);  // TTL
            return await ConsultarBaseDeDatos(id);   // a la BD (~50ms)
        });
        // si estaba (HIT): devuelve en ~1ms sin tocar la BD 🚀
    }
}

😅 El chiste más famoso de la industria: "Solo hay dos cosas difíciles en computación: la invalidación de cachés y nombrar cosas." La parte difícil no es guardar en caché: es saber cuándo borrar lo cacheado porque el dato real ya cambió (al actualizar el producto → borra su entrada del caché).

🚦 Rate Limiting: el guardia de la disco

Ya lo viste como consumidor en CP3 (el error 429); ahora del lado del que lo implementa. El rate limiting🇺🇸 Rate Limiting / 🇪🇸 Límite de tasa — Restringir cuántas peticiones puede hacer cada cliente por unidad de tiempo, para proteger el servicio de abusos y sobrecarga. limita cuántas peticiones acepta tu API por cliente y periodo. Protege de: bots maliciosos, scripts con bucles accidentales, y del "vecino ruidoso" que acapara los recursos y degrada el servicio para todos.

🪣 Token bucket (el algoritmo estrella)

Cada cliente tiene una cubeta con N fichas. Cada petición gasta una ficha; las fichas se reponen a ritmo fijo (ej. 10/segundo). ¿Cubeta vacía? → 429. Permite ráfagas cortas pero limita el promedio.

📋 Buenas prácticas al limitar

Devuelve headers informativos (X-RateLimit-Remaining, Retry-After), aplica límites por API key (no por IP, que se comparte), y usa límites distintos por endpoint: leer es barato, escribir es caro.

El método senior para optimizar rendimiento

  1. 1MIDE primero (profiling, logs de tiempos): la lentitud casi nunca está donde crees. El 80% del tiempo suele irse en el 20% del código.
  2. 2Revisa la base de datos: el sospechoso #1. Consultas sin índice (CP6), o el problema N+1 (una consulta por cada elemento de una lista en vez de una sola).
  3. 3Cachea lo repetido: ¿la misma consulta pesada 500 veces por minuto con el mismo resultado? Caché con TTL.
  4. 4Haz async lo que espera y encola lo que puede esperar (módulos 3 y 4).
  5. 5Vuelve a medir. Si no mejoró, revierte. La complejidad que no paga renta, se va.

🎯 Cómo responder preguntas de diseño de backend

Nombra el problema primero:

"Ese es un caso de trabajo pesado no urgente → cola de mensajes". Nombrar el patrón correcto vale más que recitar teoría.

Da el trade-off:

Todo patrón tiene costo: el caché puede servir datos viejos, los WebSockets complican el escalado. Mencionarlo = nivel senior.

Empieza simple:

"Empezaría con polling y migraría a WebSockets si el requisito lo exige" muestra criterio, no debilidad.
