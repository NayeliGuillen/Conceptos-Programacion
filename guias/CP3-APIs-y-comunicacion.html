Módulo 1

¿Qué es una API?

La pieza que permite que aplicaciones que no se conocen trabajen juntas.

🍽️ La analogía del mesero

Estás en un restaurante. Tú (la aplicación cliente) no entras a la cocina (el servidor) a prepararte la comida. Le pides al mesero — la API🇺🇸 API — Application Programming Interface / 🇪🇸 Interfaz de Programación de Aplicaciones — Conjunto de reglas y puntos de acceso que permite que dos programas se comuniquen sin conocer sus detalles internos. — usando el menú (la documentación). El mesero lleva tu orden a la cocina, y te trae el platillo (la respuesta). Nunca ves cómo cocinan, ni necesitas hacerlo.

🙋
Tú
App cliente
📋
Menú
Documentación de la API
🤵
Mesero
La API
👨‍🍳
Cocina
Servidor / sistema

API = Application Programming Interface (Interfaz de Programación de Aplicaciones). Es un contrato: "si me pides ESTO en ESTE formato, te respondo AQUELLO en AQUEL formato". Punto. No importa en qué lenguaje esté hecho cada lado.

¿Para qué sirve una API?

🔌 No reinventar la rueda

¿Tu app necesita mapas? No construyes un sistema de mapas: usas la API de Google Maps. ¿Pagos? La API de Stripe o PayPal. Le delegas a expertos lo que no es tu negocio.

🌉 Conectar sistemas distintos

Una app móvil en Swift, un sistema de inventario en C# y una web en JavaScript pueden hablar entre sí porque la API define un idioma común, sin importar el lenguaje interno de cada uno.

🛡️ Exponer solo lo permitido

El banco te deja consultar TU saldo vía API, pero jamás tocar su base de datos directa. La API es la puerta con reglas: qué se puede pedir, quién puede pedirlo y cuántas veces.

APIs que usas todos los días sin saberlo

  • 📱 Abres Uber: API de mapas (ubicación), API de pagos (cobro), API de SMS (código de verificación).
  • 🌦️ Ves el clima en tu celular: tu app le pregunta a una API meteorológica (como OpenWeather).
  • 🔑 "Iniciar sesión con Google": la app usa la API de Google para verificar tu identidad sin conocer tu contraseña.
  • ✈️ Buscas vuelos en un comparador: el sitio consulta las APIs de decenas de aerolíneas y junta los resultados.
  • 💬 Un bot te responde en WhatsApp: la empresa usa la API de WhatsApp Business.
  • 🛒 Rastreas tu paquete: la tienda consulta la API de la paquetería (DHL, FedEx) y te muestra el estado.

No todas las APIs son de internet

🌐 APIs Web (las de esta guía)

Se consumen por internet vía HTTP: la API del clima, de Stripe, de tu propio backend. Son las que más escucharás.

📚 APIs de librerías

Los métodos públicos de una librería también son "su API": cuando usas math.sqrt() usas la API del módulo math.

💻 APIs del sistema operativo

Windows expone APIs para que los programas abran ventanas, lean archivos o accedan a la cámara.

Módulo 2

Cliente-Servidor y HTTP

El protocolo con el que pide y responde toda la web.

🔄 El ciclo petición → respuesta

Toda la comunicación web sigue el mismo baile: el cliente🇪🇸 Cliente / 🇺🇸 Client — El programa que INICIA la comunicación y pide datos: un navegador, una app móvil, tu script de Python. (navegador, app, tu script) envía una petición🇺🇸 Request / 🇪🇸 Petición — Mensaje HTTP que el cliente envía al servidor: incluye método (GET, POST...), URL, headers y a veces un cuerpo con datos. y el servidor🇪🇸 Servidor / 🇺🇸 Server — Programa (y la máquina donde corre) que ESCUCHA peticiones, las procesa y devuelve respuestas. Nunca inicia la conversación. devuelve una respuesta🇺🇸 Response / 🇪🇸 Respuesta — Mensaje que el servidor devuelve: código de estado, headers y normalmente un cuerpo con los datos (JSON, HTML...).. El protocolo que da formato a esos mensajes es HTTP🇺🇸 HTTP — HyperText Transfer Protocol — El protocolo estándar de comunicación de la web: define cómo se estructuran las peticiones y respuestas. HTTPS es su versión cifrada..

📱 CLIENTE
"Dame el clima de Monterrey"
— petición (request) →
← respuesta (response) —
🖥️ SERVIDOR
"29°C, soleado" (JSON)

📮 Analogía del correo: la petición es una carta con destinatario (URL), tipo de trámite (método), datos del remitente (headers) y a veces un paquete adjunto (body). La respuesta siempre regresa con un sello de resultado (código de estado).

Los métodos HTTP: los verbos de la web

MétodoAcciónEjemplo real
GETLeer datos (no modifica nada)Ver la lista de productos
POSTCrear un recurso nuevoRegistrar un usuario nuevo
PUTReemplazar un recurso completoActualizar todo el perfil
PATCHModificar solo una parteCambiar solo el teléfono
DELETEEliminar un recursoBorrar un comentario
💡 ¿Notas el patrón? GET-POST-PUT/PATCH-DELETE ≈ Leer, Crear, Actualizar, Eliminar — el famoso CRUD (Create, Read, Update, Delete) que verás en CP4 con bases de datos. La web entera funciona con estas 4 operaciones.

Códigos de estado: el sello de la respuesta

Toda respuesta trae un número de 3 dígitos que resume el resultado. La primera cifra dice la familia:

2xx — Todo bien ✅

  • 200 OK — éxito general
  • 201 Created — recurso creado (tras un POST)
  • 204 No Content — éxito, sin nada que devolver

4xx — Tú te equivocaste 🙈

  • 400 Bad Request — petición mal formada
  • 401 Unauthorized — no te identificaste
  • 403 Forbidden — te identificaste, pero no tienes permiso
  • 404 Not Found — eso no existe
  • 429 Too Many Requests — pediste demasiado, espera

5xx — El servidor falló 💥

  • 500 Internal Server Error — algo tronó del lado del servidor
  • 502 Bad Gateway — un intermediario falló
  • 503 Service Unavailable — servidor saturado o en mantenimiento
🧠 Regla mnemotécnica: 4xx = "el error es del que pide" (tú); 5xx = "el error es del que responde" (el servidor). Distinguirlos es lo primero al depurar una integración: te dice de qué lado buscar el problema.

Anatomía de una URL

https://api.tienda.com/productos/42?moneda=mxn&detalle=full
Protocolo

https = HTTP cifrado. Nunca uses APIs con datos sensibles sin la S.

Dominio (host)

La dirección del servidor que atiende.

Ruta (path)

QUÉ recurso pides: el producto con id 42.

Query params

Opciones extra en pares clave=valor, tras el signo ?

Módulo 3

REST y JSON

El estilo de diseño y el formato de datos que dominan las APIs modernas.

🏛️ ¿Qué es REST?

REST🇺🇸 REST — Representational State Transfer — Estilo de arquitectura para diseñar APIs web: recursos identificados por URLs, verbos HTTP estándar y comunicación sin estado. Una API que lo sigue es "RESTful". (Representational State Transfer) no es una tecnología ni un lenguaje: es un estilo de diseño con reglas simples que hacen las APIs predecibles. Si conoces una API REST, "adivinas" cómo funcionan las demás:

1. Todo es un recurso

Usuarios, productos, pedidos... cada cosa tiene su URL: /usuarios/15 es el usuario 15. Los recursos son sustantivos, no verbos.

2. Los verbos son de HTTP

No inventes /borrarUsuario15: se usa DELETE /usuarios/15. La acción la dice el método, no la URL.

3. Sin estado (stateless)

Cada petición es independiente y lleva TODO lo necesario (incluida tu identificación). El servidor no "recuerda" la petición anterior.

Quiero...Petición REST
Ver todos los productosGET /productos
Ver el producto 42GET /productos/42
Crear un productoPOST /productos (+ datos en el body)
Actualizar el producto 42PUT /productos/42 (+ datos en el body)
Eliminar el producto 42DELETE /productos/42

📦 JSON: el idioma de los datos

JSON🇺🇸 JSON — JavaScript Object Notation — Formato de texto ligero para intercambiar datos estructurados. Usa pares clave-valor y listas; todos los lenguajes lo leen y escriben. (JavaScript Object Notation) es el formato en que las APIs REST envían y reciben datos. Es texto plano, legible por humanos, y ¿te suena familiar? — se parece muchísimo a los diccionarios de CP1:

{
  "nombre": "Laptop Dell XPS",        ← texto entre comillas dobles
  "precio": 24999.90,                  ← números sin comillas
  "disponible": true,                  ← booleanos: true / false
  "categorias": ["computo", "oficina"], ← listas entre corchetes
  "vendedor": {                        ← objetos anidados entre llaves
    "id": 7,
    "ciudad": "Monterrey"
  },
  "descuento": null                    ← null = sin valor
}
📌 Reglas de oro del JSON: claves SIEMPRE entre comillas dobles, sin comas finales, sin comentarios. Un JSON inválido por una coma es el clásico error de integración.
🔄 Serializar = convertir tu objeto (Python/C#) a texto JSON para enviarlo. Deserializar = convertir el JSON recibido de vuelta a un objeto usable en tu lenguaje.

Una respuesta real, diseccionada

Así se ve la conversación completa cuando pides GET https://api.tienda.com/productos/42:

── RESPUESTA DEL SERVIDOR ──────────────────────────
HTTP/1.1 200 OK                      ← código de estado: éxito
Content-Type: application/json       ← header: "el body es JSON"
Cache-Control: max-age=3600          ← header: "puedes guardarlo 1 hora"

{                                     ← el body: los datos que pediste
  "id": 42,
  "nombre": "Laptop Dell XPS",
  "precio": 24999.90,
  "disponible": true
}

Módulo 4

Consumir APIs con Código

Manos al teclado: pide datos reales desde Python y C#.

🌦️ Ejemplo completo: consultar una API pública

Vamos a pedir un usuario de prueba a jsonplaceholder.typicode.com, una API pública y gratuita para practicar (¡pruébala!). El flujo siempre es el mismo: armar la petición → enviarla → revisar el estado → deserializar el JSON.

import requests    # librería estándar de facto: pip install requests

# 1. Enviar la petición GET
respuesta = requests.get("https://jsonplaceholder.typicode.com/users/1")

# 2. Revisar el código de estado
if respuesta.status_code == 200:
    # 3. Deserializar: JSON → diccionario de Python
    usuario = respuesta.json()
    print(usuario["name"])       # Leanne Graham
    print(usuario["email"])      # Sincere@april.biz
else:
    print(f"Error: {respuesta.status_code}")

# POST: crear un recurso enviando JSON en el body
nuevo = {"title": "Aprender APIs", "completed": False}
r = requests.post("https://jsonplaceholder.typicode.com/todos", json=nuevo)
print(r.status_code)             # 201 Created
using System.Net.Http;
using System.Net.Http.Json;   // helpers para JSON

// HttpClient: el "requests" de C#. Se crea UNA vez y se reutiliza
var http = new HttpClient();

// 1. Enviar la petición GET (async: no congela la app mientras espera)
var respuesta = await http.GetAsync("https://jsonplaceholder.typicode.com/users/1");

// 2. Revisar el código de estado
if (respuesta.IsSuccessStatusCode)
{
    // 3. Deserializar: JSON → objeto C#
    var usuario = await respuesta.Content.ReadFromJsonAsync<Usuario>();
    Console.WriteLine(usuario.Name);    // Leanne Graham
    Console.WriteLine(usuario.Email);   // Sincere@april.biz
}

// POST: crear un recurso enviando JSON en el body
var nuevo = new { title = "Aprender APIs", completed = false };
var r = await http.PostAsJsonAsync("https://jsonplaceholder.typicode.com/todos", nuevo);
Console.WriteLine((int)r.StatusCode);   // 201

// La clase que "recibe" el JSON (sus propiedades = claves del JSON)
record Usuario(string Name, string Email);

💡 Nota la diferencia de estilo: Python deserializa a un diccionario flexible; C# suele deserializar a una clase tipada (aquí un record). Mismo concepto, filosofías distintas — dinámico vs. estático, como viste en CP1.

Herramientas para explorar APIs sin programar

📬 Postman

App gráfica para armar y enviar peticiones con clics: eliges método, URL, headers y body, y ves la respuesta formateada. Es la herramienta estándar para probar una API antes (y después) de escribir código.

Ideal para: explorar una API nueva, reproducir errores, compartir colecciones de peticiones con tu equipo.

⌨️ curl

El clásico de línea de comandos, disponible en casi cualquier máquina:

# GET simple
curl https://jsonplaceholder.typicode.com/users/1

# POST con JSON
curl -X POST -H "Content-Type: application/json" \
     -d '{"title":"Aprender APIs"}' \
     https://jsonplaceholder.typicode.com/todos
🎯 Flujo profesional al integrar una API nueva: 1) Lee la documentación (el "menú"). 2) Prueba los endpoints en Postman hasta que respondan lo esperado. 3) Ya que entiendes la API, escribe el código. 4) Maneja SIEMPRE los casos de error (4xx/5xx, timeouts) — la red falla más de lo que crees.

Módulo 5

Autenticación y Seguridad

¿Quién eres y qué tienes permitido hacer?

🔑 Los métodos de autenticación, del más simple al más robusto

1. API Key — la llave sencilla

Una cadena secreta que te da el proveedor y envías en cada petición (en un header o query param). Como la clave de acceso de un gimnasio: identifica tu cuenta y mide tu consumo.

GET /clima?ciudad=Monterrey
X-Api-Key: tu_clave_secreta_aqui

2. Token Bearer / JWT — el gafete temporal

Te identificas UNA vez (login) y recibes un token🇺🇸 Token — Credencial temporal que el cliente presenta en cada petición tras iniciar sesión. El JWT (JSON Web Token) es el formato más común: lleva datos firmados y fecha de expiración. con expiración que presentas en cada petición. Como el gafete de visitante de un edificio: te lo dan en recepción y lo muestras en cada piso, hasta que expira.

GET /mis-pedidos
Authorization: Bearer eyJhbGciOiJIUzI1NiIs...

3. OAuth 2.0 — el permiso delegado

El estándar detrás de "Iniciar sesión con Google/Facebook". Permite que una app acceda a TUS datos en otro servicio sin darle tu contraseña: autorizas en Google, y la app recibe un token limitado a lo que aceptaste. Como el valet parking: le das una llave que solo enciende el coche, no abre la cajuela.

Autenticación vs. Autorización (no son lo mismo)

🪪 Autenticación — ¿QUIÉN eres?

Probar tu identidad: usuario/contraseña, API key, huella. Si falla → 401 Unauthorized.

🚪 Autorización — ¿QUÉ puedes hacer?

Ya sé quién eres; ¿tienes permiso para ESTO? Un usuario normal no puede borrar cuentas ajenas. Si falla → 403 Forbidden.

Reglas de seguridad que nadie te perdona romper

  • 🚫NUNCA pongas API keys en el código fuente ni las subas a GitHub. Van en variables de entorno o en un gestor de secretos. (Hay bots escaneando GitHub 24/7 buscando llaves filtradas para abusarlas.)
  • 🔒Siempre HTTPS: sin la S, cualquiera en la red puede leer tus peticiones — incluidos tus tokens.
  • ⏳Tokens con expiración corta: si se filtra uno, el daño dura minutos, no meses.
  • 🤏Principio de mínimo privilegio: pide (y otorga) solo los permisos necesarios. Si tu app solo lee, no pidas permiso de escritura.
  • 🧪Valida todo lo que recibes: nunca confíes en que el cliente envía datos correctos o bien intencionados.

Módulo 6

Más allá de REST

Webhooks, GraphQL, SOAP... y tu primera API propia.

🔔 Webhooks: la API al revés

Con una API normal, TÚ preguntas ("¿ya pagaron?, ¿ya pagaron?..."). Con un webhook🇺🇸 Webhook — Mecanismo donde el SERVIDOR te avisa a ti: registras una URL tuya y el servicio la llama automáticamente cuando ocurre un evento (pago recibido, pedido enviado...)., el servicio TE AVISA: registras una URL tuya y cuando ocurre el evento (pago recibido), ellos llaman a tu URL con los datos. Es el timbre de la casa: en vez de asomarte a la puerta cada minuto, el visitante toca cuando llega.

🔄 Polling (sin webhook)

Preguntar cada X segundos "¿ya?". Simple pero desperdicia recursos y se entera tarde.

🔔 Webhook

Te notifican al instante, solo cuando pasa algo. Así te avisa Stripe de un pago o GitHub de un push.

Otros estilos de API que debes ubicar

EstiloIdea centralCuándo lo verás
RESTRecursos + verbos HTTP + JSON. El estándar de facto.La gran mayoría de las APIs modernas

Conceptos de API que preguntan en entrevistas

⏱️ Rate Limiting

Límite de peticiones por minuto/hora para proteger al servidor ("100 peticiones/min"). Si lo excedes: 429. Por eso las APIs serias piden identificarte hasta para leer.

🏷️ Versionado

Las APIs evolucionan sin romper a sus clientes viejos: /v1/productos sigue viva mientras /v2/productos agrega cambios. Nunca cambies un contrato publicado: crea versión nueva.

📄 Paginación

Nadie devuelve 1 millón de registros de golpe: se sirven por páginas (?page=2&limit=50). Al consumir APIs, revisa siempre si hay "página siguiente".

🏗️ Bonus: así de fácil es CREAR una API

No solo se consumen: tarde o temprano crearás la tuya. Mira lo poco que se necesita para un endpoint funcional:

from flask import Flask, jsonify    # pip install flask

app = Flask(__name__)

@app.route("/api/saludo/<nombre>")   # define el endpoint
def saludar(nombre):
    return jsonify({"mensaje": f"¡Hola, {nombre}!"})

app.run()   # ya tienes una API en http://localhost:5000
# GET /api/saludo/Nayeli → {"mensaje": "¡Hola, Nayeli!"}
// ASP.NET Core Minimal API (Program.cs completo)
var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();

// define el endpoint
app.MapGet("/api/saludo/{nombre}",
    (string nombre) => new { mensaje = $"¡Hola, {nombre}!" });

app.Run();   // ya tienes una API en http://localhost:5000
// GET /api/saludo/Nayeli → {"mensaje": "¡Hola, Nayeli!"}
