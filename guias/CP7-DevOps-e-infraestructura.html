Módulo 1

Git Avanzado

Rebase, cherry-pick y compañía: las herramientas que separan al usuario de Git del que lo domina.

🔀 Merge vs. Rebase: la pregunta eterna

Ambos integran cambios de una rama a otra, pero cuentan la historia de forma distinta:

🔗 MERGE — historia fiel

main:    A---B---C-------M
                  \     /
tu rama:           D---E

Crea un commit de fusión (M) que une las dos líneas. La historia muestra lo que realmente pasó, con sus bifurcaciones. Seguro pero el historial se "enreda" con muchos merges.

📏 REBASE — historia lineal

main:    A---B---C---D'---E'

(tus commits D y E se "replantan"
 encima del main actualizado)

Toma tus commits y los re-aplica sobre la punta de main, como si hubieras empezado hoy. Historia limpia y lineal... pero REESCRIBE los commits (D→D').

🚨 LA regla de oro del rebase: nunca hagas rebase de commits que YA compartiste (pusheados a una rama que otros usan). Reescribir historia compartida rompe el repositorio de tus compañeros. Rebase en tu rama local privada: ✅. Rebase de main: ❌❌❌.

La caja de herramientas avanzada

🍒 cherry-pick — "solo ese commit"

Copia UN commit específico de otra rama a la tuya. Caso típico: un hotfix hecho en main que necesitas también en la rama de release.

git cherry-pick a1b2c3d   # trae solo ese commit

📦 stash — "guárdame esto tantito"

Guarda tus cambios sin commitear para cambiar de rama con las manos limpias, y recupéralos después.

git stash          # guarda el trabajo a medias
git stash pop      # recupéralo donde ibas

🕵️ bisect — el detective binario

¿Un bug apareció "en algún momento de los últimos 200 commits"? Bisect hace búsqueda binaria (¡O(log n) de CP4!): te va dando commits intermedios para probar hasta aislar el culpable en ~8 pasos.

git bisect start
git bisect bad            # el actual está roto
git bisect good v2.1      # esa versión funcionaba

✏️ rebase interactivo — pulir antes de publicar

Antes de abrir el PR, limpia tu rama: une commits pequeños (squash), renombra mensajes, reordena. Tu PR llega con 3 commits claros en vez de 14 "fix typo".

git rebase -i HEAD~5   # edita tus últimos 5 commits

⚔️ Resolver conflictos como profesional (paso a paso)

# Al hacer merge/rebase, Git marca los conflictos así en el archivo:
<<<<<<< HEAD
precio_final = subtotal * 1.16        # tu versión
=======
precio_final = subtotal * (1 + IVA)   # la versión de tu colega
>>>>>>> feature/impuestos
  1. 1. git status — lista los archivos en conflicto. Respira: es normal.
  2. 2. Abre cada archivo y decide: ¿tu versión, la suya, o una combinación? Entiende ambas antes de borrar — el error clásico es pisar el trabajo del colega sin leerlo.
  3. 3. Borra los marcadores <<<< ==== >>>> y deja el código final.
  4. 4. ¡Corre las pruebas! Que "compile" no significa que la combinación funcione.
  5. 5. git add . y git commit (o git rebase --continue). Si te enredaste: git merge --abort deshace todo y vuelves a empezar.

💡 Prevención: ramas cortas que viven pocos días + git pull frecuente = conflictos chiquitos y fáciles. Las ramas de 3 semanas producen conflictos de terror.

Módulo 2

CI/CD

La línea de ensamblaje: del push al despliegue sin manos humanas.

🏭 Anatomía de un pipeline

Un pipeline🇺🇸 Pipeline — Secuencia automatizada de pasos (compilar, probar, desplegar) que se dispara con cada push. Si un paso falla, la línea se detiene y nada roto llega a producción. es una línea de ensamblaje con control de calidad: cada push pasa por estaciones, y si UNA falla, el producto no avanza. CI (Integración Continua) = compilar + probar cada cambio automáticamente. CD (Despliegue Continuo) = si todo pasó, publicar automáticamente.

push → 🔨 Build → 🧪 Tests → 🔍 Lint/Análisis → 📦 Empaquetar → 🚀 Deploy

Así se ve un pipeline real de GitHub Actions (vive en .github/workflows/ci.yml dentro de tu repo):

name: CI
on:
  push:                          # se dispara con cada push...
    branches: [main]
  pull_request:                 # ...y con cada PR

jobs:
  build-and-test:
    runs-on: ubuntu-latest      # una máquina limpia por corrida
    steps:
      - uses: actions/checkout@v4          # 1. clona el código
      - uses: actions/setup-dotnet@v4      # 2. instala .NET (o setup-python)
        with: { dotnet-version: '8.0' }
      - run: dotnet build                   # 3. compila
      - run: dotnet test                    # 4. corre TODAS las pruebas
        # si algo falla aquí, el PR se marca en rojo y no se puede unir

Las herramientas y los matices

🐙 GitHub Actions

Integrado a GitHub, YAML simple, gratis para repos públicos. El punto de entrada recomendado — configúralo en tus proyectos personales hoy mismo.

🦊 GitLab CI

Equivalente para GitLab (.gitlab-ci.yml). Muy usado en empresas que alojan su propio GitLab.

🎩 Jenkins

El veterano auto-hospedado: flexible pero exige mantenimiento. Lo verás en empresas grandes con procesos establecidos.

📖 Delivery vs. Deployment: Continuous Delivery = todo queda LISTO para desplegar, pero un humano aprueba el botón final. Continuous Deployment = ni botón: si las pruebas pasan, sale a producción solo. La mayoría de las empresas hace Delivery.
🛡️ El pipeline es tu guardián: conecta todo lo aprendido — corre las pruebas (CP4), aplica las migraciones (CP6), construye la imagen Docker (módulo 3) y despliega a la nube (módulo 4). Sin pruebas buenas, el CD es solo una forma más rápida de romper producción.

Módulo 3

Docker y Kubernetes

El fin definitivo de "en mi máquina sí funciona".

📦 El contenedor de barco

Antes de los contenedores marítimos, cargar un barco era un caos: cada mercancía con su forma. El contenedor estandarizó TODO: no importa qué haya adentro, todos se apilan y transportan igual. Docker🇺🇸 Docker — Plataforma de contenedores: empaqueta tu app CON todas sus dependencias (runtime, librerías, configuración) en una unidad estándar que corre idéntica en cualquier máquina. hace eso con software: empaqueta tu app con todo lo que necesita (versión exacta de Python/.NET, librerías, configuración) en un contenedor que corre idéntico en tu laptop, el servidor del colega y la nube.

🍪 Imagen = la receta congelada

Plantilla inmutable con tu app y sus dependencias. Se construye UNA vez y se comparte en un registro (Docker Hub, ECR). ¿Te suena? Es el patrón clase→objeto de CP2.

🏃 Contenedor = la instancia corriendo

Una imagen en ejecución. Puedes correr 1 o 50 contenedores de la misma imagen. Ligeros (comparten el kernel del sistema, no son máquinas virtuales completas) y desechables.

# Dockerfile: la "receta" de tu imagen, paso a paso
FROM python:3.12-slim          # parte de una imagen base oficial
WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt   # instala dependencias
COPY . .                       # copia tu código
CMD ["python", "app.py"]      # qué ejecutar al arrancar

# En la terminal:
# docker build -t mi-api .        ← construye la imagen
# docker run -p 8000:8000 mi-api  ← corre el contenedor

🧩 docker-compose orquesta VARIOS contenedores locales de una vez: tu API + PostgreSQL + Redis levantados con un solo docker compose up. Todo el entorno de desarrollo, reproducible, en un archivo YAML del repo.

☸️ Kubernetes: el director de orquesta

Un contenedor está bien. ¿Pero 300 contenedores en 20 servidores, que deben reiniciarse si mueren, escalar si hay tráfico y actualizarse sin downtime? Eso es orquestación🇺🇸 Orchestration — Gestionar automáticamente muchos contenedores: dónde corren, cuántas réplicas hay, reinicios ante fallos y actualizaciones sin downtime. Kubernetes es el estándar., y Kubernetes (K8s) es el estándar. Tú le declaras el estado deseado ("quiero 5 réplicas de mi API siempre vivas") y él lo mantiene: si un contenedor muere a las 3 AM, K8s lo revive solo.

Pod
La unidad mínima: 1+ contenedores juntos
Deployment
"Mantén N réplicas de este pod vivas"
Service
La puerta estable que balancea entre pods
Ingress
La entrada HTTP desde el exterior
⚖️ Honestidad senior: Kubernetes es poderoso y COMPLEJO. Para una app mediana, un servicio administrado simple (App Service, Cloud Run, ECS) suele bastar. Aprende los conceptos de K8s para las entrevistas y para leer arquitecturas — pero no lo metas a tu proyecto personal "porque se ve pro".

Módulo 4

La Nube: AWS, Azure y GCP

Tres nubes, los mismos conceptos. Domina una a fondo.

🗺️ El diccionario de las 3 nubes

Los tres gigantes ofrecen los MISMOS servicios con nombres distintos. Aprende los conceptos una vez y "traduce" entre nubes con esta tabla:

Necesito...🟧 AWS🟦 Azure🟥 GCP
Máquinas virtualesEC2Virtual MachinesCompute Engine
Guardar archivos/objetosS3Blob StorageCloud Storage
Base de datos SQL administradaRDSAzure SQLCloud SQL
Funciones serverlessLambdaAzure FunctionsCloud Functions
Contenedores administradosECS / EKSContainer Apps / AKSCloud Run / GKE
Colas de mensajesSQSService BusPub/Sub
Gestor de secretosSecrets ManagerKey VaultSecret Manager
🎯 ¿Cuál aprender a fondo? La que use tu empresa o tu mercado objetivo. Sin contexto: AWS tiene la mayor cuota y demanda laboral; Azure domina el mundo corporativo/.NET (¡natural si vienes de C#!); GCP brilla en datos/ML. Los conceptos se transfieren en un 80% — lo importante es dominar UNA de verdad.

Conceptos transversales que sí o sí debes manejar

⚡ Serverless

Subes una FUNCIÓN, no un servidor: la nube la ejecuta cuando llega el evento y cobra por milisegundo de ejecución. Cero servidores que administrar; ideal para tareas esporádicas (procesar un archivo subido, un webhook). Trade-off: arranque en frío y límites de tiempo.

🌍 Regiones y zonas de disponibilidad

Región = ubicación geográfica (Virginia, São Paulo). Zona = centro de datos independiente dentro de la región. Desplegar en 2+ zonas = sobrevivir a que un centro de datos entero se caiga.

💸 El modelo de costos

Pagas por lo que usas... y por lo que OLVIDASTE apagar. La historia de terror universal: la instancia de pruebas que corrió 8 meses. Regla: presupuestos con alertas desde el día uno, y apagar todo lo que no sirve.

🔑 IAM (identidad y permisos)

QUIÉN puede hacer QUÉ sobre CUÁL recurso. El principio de menor privilegio (CP8) aplicado a la nube: la app que solo lee de S3 no necesita permiso de borrar buckets. La mayoría de los hackeos de nube empiezan por permisos flojos.

Módulo 5

Infraestructura como Código

Tu infraestructura en un repositorio, no en la memoria de alguien.

🏗️ El problema del "ClickOps"

Crear infraestructura a clics en la consola web funciona... hasta que: nadie recuerda qué se configuró, el ambiente de staging es "parecido pero no igual" a producción, y reconstruir todo tras un desastre toma semanas. IaC🇺🇸 IaC — Infrastructure as Code — Definir servidores, redes y bases de datos en archivos de código versionados. La infraestructura se crea, modifica y reconstruye ejecutando el código, no a clics. (Infraestructura como Código) lo resuelve: describes tu infraestructura en archivos versionados en Git, y una herramienta la crea por ti — idéntica cada vez. Los planos del arquitecto en lugar de instrucciones verbales al albañil.

# main.tf — Terraform (lenguaje HCL): describe QUÉ quieres, no CÓMO crearlo
resource "aws_instance" "api_server" {
  ami           = "ami-0abc123"       # imagen del sistema
  instance_type = "t3.small"          # tamaño de la máquina
  tags = { Name = "api-produccion" }
}

resource "aws_s3_bucket" "reportes" {
  bucket = "reportes-empresa-2026"
}

# Flujo de trabajo:
# terraform plan   ← te MUESTRA qué va a crear/cambiar/destruir (revisas)
# terraform apply  ← lo ejecuta

📜 Declarativo

Describes el estado FINAL deseado; Terraform calcula los pasos. Si ya existe, no hace nada (idempotencia — ¿te suena de CP5?).

🗂️ El estado (state)

Terraform guarda un registro de lo que creó, para calcular diferencias. En equipo, el state vive compartido y con bloqueo (ej. en S3).

🔁 Reproducible

¿Nuevo ambiente? ¿Región nueva? ¿Desastre? Corres el código y renace TODO, idéntico, en minutos.

🛠️ El ecosistema

  • Terraform — el estándar multi-nube (AWS, Azure, GCP con la misma herramienta). Por aquí se empieza.
  • CloudFormation — el nativo de AWS; Bicep — el nativo de Azure. Solo funcionan en su nube.
  • Ansible — pariente: configura lo que hay DENTRO de los servidores (paquetes, archivos).

🧠 Por qué a los seniors les importa tanto

La IaC convierte la infraestructura en algo revisable (¡pull requests para cambios de servidores!), auditable (Git dice quién cambió qué y cuándo) y recuperable (el plan de desastres es "terraform apply").

Además, elimina el "servidor mascota" que solo Juan sabe configurar... y Juan renunció.

Módulo 6

Monitoreo, Logging y Nginx

Si producción se enferma, ¿cómo te enteras? ¿Y quién reparte el tráfico?

🩺 Los 3 signos vitales de un sistema (observabilidad)

📜 Logs — el diario

Cada evento registrado: "usuario 7 inició sesión", "error al cobrar pedido 1001". La clave profesional: logs estructurados (JSON con campos) en vez de texto suelto — así se filtran y buscan.

Herramientas: ELK (Elasticsearch + Logstash + Kibana), Grafana Loki, CloudWatch Logs.

📈 Métricas — los números vitales

Valores en el tiempo: peticiones/segundo, latencia p95, % de CPU, errores por minuto. Prometheus las recolecta; Grafana las grafica en dashboards; las alertas te despiertan si algo se sale de rango.

La pregunta que responden: "¿está sano el sistema AHORA y hacia dónde va?"

🚨 Errores — el radar de excepciones

Sentry captura cada excepción no manejada en producción CON su stack trace, usuario afectado y frecuencia. Te enteras del bug antes que los usuarios lo reporten.

Agrupa errores repetidos: "este NullReference pasó 3,400 veces desde el deploy de ayer" → rollback.

🧠 Regla senior: si no se puede medir, no está en producción. El deploy sin monitoreo es manejar de noche sin faros: quizá no choques hoy, pero no lo sabrás hasta el golpe.

🚪 Nginx: el recepcionista del edificio

Nginx es un servidor web que casi siempre actúa como reverse proxy🇺🇸 Reverse Proxy — Servidor intermedio que recibe TODAS las peticiones del exterior y las reenvía a tus servidores internos. Centraliza TLS, balanceo, caché y protección.: el único que da la cara a internet. Como el recepcionista de un edificio corporativo: recibe a todos, revisa a dónde van, y los dirige al piso correcto — nadie deambula directo a las oficinas.

# nginx.conf — balanceo de carga entre 3 servidores de tu API
upstream mi_api {
    server 10.0.0.11:8000;    # servidor 1
    server 10.0.0.12:8000;    # servidor 2
    server 10.0.0.13:8000;    # servidor 3
    # por defecto: round-robin (turnos rotativos)
}

server {
    listen 443 ssl;               # HTTPS terminado aquí (ver CP8)
    server_name api.miempresa.com;

    location / {
        proxy_pass http://mi_api;  # reparte a los 3 servidores
    }
}

⚖️ Balanceo de carga

Reparte el tráfico entre N servidores (round-robin, menos conexiones...). Si uno muere, deja de enviarle tráfico (health checks). Es el ingrediente básico de la escalabilidad horizontal (CP9).

🧰 Los otros roles de Nginx

Terminar TLS/HTTPS en un solo punto, servir archivos estáticos ultrarrápido, cachear respuestas, comprimir, y aplicar rate limiting antes de que el tráfico toque tu app.

Preguntas frecuentes de DevOps

Frases clave en inglés para entrevistas / Key Phrases

Hablar del flujo de despliegue

"Every push triggers the pipeline: build, test, deploy."

Cada push dispara el pipeline: compilar, probar, desplegar.

"The app is containerized, so it runs the same everywhere."

La app está en contenedores, así que corre igual en todos lados.

"Infrastructure is managed with Terraform and reviewed in PRs."

La infraestructura se maneja con Terraform y se revisa en PRs.

"We rolled back within minutes thanks to versioned releases."

Revertimos en minutos gracias a los releases versionados.

Hablar de operación

"Grafana dashboards track latency and error rates."

Los dashboards de Grafana siguen la latencia y la tasa de errores.

"Sentry alerted us before users noticed the bug."

Sentry nos alertó antes de que los usuarios notaran el bug.

"Nginx sits in front as a reverse proxy and load balancer."

Nginx va al frente como reverse proxy y balanceador de carga.

"I never rebase shared branches."

Nunca hago rebase de ramas compartidas.
