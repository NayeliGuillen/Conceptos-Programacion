Módulo 1

Paradigmas de Programación

Un paradigma es una forma de PENSAR y organizar el código. La POO es una de varias — y hay que saber por qué ganó tanto terreno.

🗺️ ¿Qué es un paradigma?

Un paradigma🇪🇸 Paradigma / 🇺🇸 Paradigm — Estilo o filosofía para estructurar programas: cómo se organiza el código y cómo se modela el problema. es como el estilo arquitectónico de una casa: con los mismos ladrillos (variables, funciones, bucles) puedes construir estilos muy distintos. Los tres paradigmas que más escucharás:

📜 Procedural / Imperativo

El programa es una lista de pasos de arriba a abajo, organizada en funciones. Así se escriben los scripts simples. Ej: C, Pascal, Python básico.

🧩 Orientado a Objetos (POO)

El programa se organiza en objetos: piezas que juntan datos + comportamiento, imitando cosas del mundo real. Ej: C#, Java, y Python cuando usas clases.

λ Funcional

El programa se arma combinando funciones puras que no modifican nada externo. Ej: Haskell, F#, y las funciones lambda/LINQ que ya existen en Python y C#.

💡 Python y C# son multiparadigma: soportan los tres estilos. Un buen programador elige el estilo según el problema, no por moda.

¿Por qué nació la POO?

El problema: el "código espagueti" 🍝

En los 60s-70s los programas crecieron tanto que se volvieron inmanejables: cientos de funciones y variables globales tocándose entre sí. Cambiar una línea rompía diez cosas en lugares inesperados.

La POO propuso: agrupa cada dato con las funciones que lo manipulan en una "cápsula" llamada objeto. Así, el estado de cada pieza solo lo toca quien debe tocarlo.

Breve historia

  • 1967Simula (Noruega) introduce las clases y objetos.
  • 1972Smalltalk populariza el término "orientado a objetos".
  • 1985+C++ lleva la POO al mundo masivo.
  • 1995Java hace de la POO el estándar empresarial.
  • 2000C# nace como lenguaje POO moderno de Microsoft.

Módulo 2

Clases y Objetos

El molde de galletas y las galletas: la idea central de toda la POO.

🍪 La analogía del molde de galletas

La CLASE es el molde

Una clase🇪🇸 Clase / 🇺🇸 Class — Plantilla o molde que define qué datos (atributos) y qué comportamientos (métodos) tendrán los objetos creados a partir de ella. define la FORMA: qué datos tendrá (atributos) y qué sabrá hacer (métodos). El molde no es una galleta — es la definición.

El OBJETO es la galleta

Un objeto🇪🇸 Objeto / 🇺🇸 Object — Instancia concreta de una clase, con sus propios valores en los atributos. De una clase puedes crear tantos objetos como quieras. es una instancia🇪🇸 Instancia / 🇺🇸 Instance — Cada objeto concreto creado a partir de una clase. "Instanciar" = crear un objeto con new (C#) o llamando la clase (Python). concreta creada con ese molde. Puedes hacer 50 galletas del mismo molde, cada una con su propio chispazo de chocolate (sus propios valores).

class Perro:
    # CONSTRUCTOR: se ejecuta al crear cada objeto
    def __init__(self, nombre, edad):
        self.nombre = nombre     # atributo (dato del objeto)
        self.edad = edad

    # MÉTODO: comportamiento del objeto
    def ladrar(self):
        return f"{self.nombre} dice: ¡Guau!"

# Crear OBJETOS (instancias) — cada uno con sus propios datos
firulais = Perro("Firulais", 3)
luna = Perro("Luna", 5)

print(firulais.ladrar())   # Firulais dice: ¡Guau!
print(luna.edad)           # 5
class Perro
{
    // ATRIBUTOS (en C#: propiedades)
    public string Nombre { get; set; }
    public int Edad { get; set; }

    // CONSTRUCTOR: se ejecuta al crear cada objeto
    public Perro(string nombre, int edad)
    {
        Nombre = nombre;
        Edad = edad;
    }

    // MÉTODO: comportamiento del objeto
    public string Ladrar() => $"{Nombre} dice: ¡Guau!";
}

// Crear OBJETOS (instancias) — cada uno con sus propios datos
var firulais = new Perro("Firulais", 3);
var luna = new Perro("Luna", 5);

Console.WriteLine(firulais.Ladrar());  // Firulais dice: ¡Guau!
Console.WriteLine(luna.Edad);           // 5

💡 self (Python) y this (C#) significan "este objeto en particular". Cuando Firulais ladra, self/this ES Firulais; cuando Luna ladra, ES Luna.

Las 3 piezas de toda clase

📊 Atributos

Los datos que cada objeto guarda: nombre, edad, saldo, color. En C# suelen ser propiedades🇺🇸 Property — En C#, atributo con get/set integrados que permite controlar cómo se lee y escribe el dato. con get/set. Responden a "¿qué ES / qué TIENE?"

⚡ Métodos

Las acciones que el objeto sabe hacer: ladrar(), depositar(), enviar_correo(). Son funciones que viven dentro de la clase. Responden a "¿qué SABE HACER?"

🏗️ Constructor

El método especial que se ejecuta al crear el objeto, para dejarlo listo con sus valores iniciales. __init__ en Python; un método con el nombre de la clase en C#.

Ejemplo realista: una cuenta bancaria

class CuentaBancaria:
    def __init__(self, titular):
        self.titular = titular
        self.saldo = 0            # toda cuenta nueva empieza en 0

    def depositar(self, monto):
        if monto <= 0:
            raise ValueError("El monto debe ser positivo")
        self.saldo += monto

    def retirar(self, monto):
        if monto > self.saldo:
            raise ValueError("Fondos insuficientes")
        self.saldo -= monto

cuenta = CuentaBancaria("Nayeli")
cuenta.depositar(1000)
cuenta.retirar(250)
print(cuenta.saldo)    # 750
class CuentaBancaria
{
    public string Titular { get; }
    public decimal Saldo { get; private set; }   // solo la clase lo modifica

    public CuentaBancaria(string titular)
    {
        Titular = titular;
        Saldo = 0;               // toda cuenta nueva empieza en 0
    }

    public void Depositar(decimal monto)
    {
        if (monto <= 0)
            throw new ArgumentException("El monto debe ser positivo");
        Saldo += monto;
    }

    public void Retirar(decimal monto)
    {
        if (monto > Saldo)
            throw new InvalidOperationException("Fondos insuficientes");
        Saldo -= monto;
    }
}

var cuenta = new CuentaBancaria("Nayeli");
cuenta.Depositar(1000);
cuenta.Retirar(250);
Console.WriteLine(cuenta.Saldo);   // 750
🧠 Esto ES la POO: el dato (saldo) y las reglas para tocarlo (depositar valida positivo, retirar valida fondos) viven juntos en la misma cápsula. Nadie puede dejar el saldo en un estado inválido "desde afuera". Compáralo con tener una variable global saldo que cualquier parte del programa puede pisar.

💊 Pilar 1: Encapsulamiento — la cápsula de medicina

El encapsulamiento🇪🇸 Encapsulamiento / 🇺🇸 Encapsulation — Ocultar los datos internos de un objeto y permitir su acceso solo mediante métodos controlados. Protege el estado de modificaciones inválidas. junta datos y métodos en una cápsula y esconde el interior. Como una cápsula de medicina: te tomas la cápsula completa; no abres el polvito para administrártelo tú. Los datos internos son privados y solo se tocan por los métodos públicos que la clase ofrece.

ModificadorQuién puede acceder🐍 Python#️⃣ C#
PúblicoTodo el mundonombre (normal)public
PrivadoSolo la propia clase__nombre (convención _ o __)private
ProtegidoLa clase y sus hijas_nombre (convención)protected

⚠️ Detalle honesto: en Python la privacidad es por convención (el guion bajo dice "no me toques", pero técnicamente se puede). En C# el compilador la impone: acceder a un private desde fuera ni siquiera compila.

class Termostato:
    def __init__(self):
        self.__temperatura = 22      # __ = privado (convención fuerte)

    # @property permite leerla como atributo, con control
    @property
    def temperatura(self):
        return self.__temperatura

    @temperatura.setter
    def temperatura(self, valor):
        if 10 <= valor <= 30:         # la REGLA vive dentro de la clase
            self.__temperatura = valor
        else:
            raise ValueError("Rango permitido: 10–30°C")

t = Termostato()
t.temperatura = 25     # ✅ pasa por el setter y su validación
t.temperatura = 80     # ❌ ValueError: imposible dejarlo inválido
class Termostato
{
    private int _temperatura = 22;   // privado: el compilador lo protege

    public int Temperatura
    {
        get => _temperatura;
        set
        {
            if (value >= 10 && value <= 30)   // la REGLA vive en la clase
                _temperatura = value;
            else
                throw new ArgumentOutOfRangeException("Rango: 10–30°C");
        }
    }
}

var t = new Termostato();
t.Temperatura = 25;   // ✅ pasa por el setter y su validación
t.Temperatura = 80;   // ❌ excepción: imposible dejarlo inválido

📺 Pilar 2: Abstracción — el control remoto

La abstracción🇪🇸 Abstracción / 🇺🇸 Abstraction — Exponer solo lo esencial de un objeto y ocultar los detalles de implementación. El usuario ve QUÉ hace, no CÓMO lo hace. es mostrar qué hace algo sin exponer cómo lo hace. Tu control remoto tiene un botón "subir volumen": no necesitas saber nada de señales infrarrojas ni circuitos. La clase ofrece métodos simples (enviar_correo(destinatario)) y esconde el caos interno (servidores SMTP, encriptación, reintentos...).

Encapsulamiento vs. Abstracción (pregunta de entrevista ⭐)

Abstracción = decisión de diseño: qué mostrar (la interfaz simple). Encapsulamiento = el mecanismo: cómo ocultar y proteger lo interno (private, properties). La abstracción es el "menú del restaurante"; el encapsulamiento es "la puerta de la cocina cerrada".

Ya usas abstracción todos los días

print(), Console.WriteLine(), lista.sort()... ¿Sabes CÓMO ordenan internamente? No, y no importa. Eso es una buena abstracción: la usas sin abrirla.

👨‍👧 Pilar 3: Herencia — rasgos de familia

La herencia🇪🇸 Herencia / 🇺🇸 Inheritance — Mecanismo por el cual una clase (hija/derivada) obtiene los atributos y métodos de otra (padre/base), pudiendo agregar o modificar comportamiento. permite que una clase hija reciba todo lo de una clase padre y le agregue o cambie lo suyo. Como los rasgos de familia: heredas los ojos de tu mamá, pero tienes tu propia personalidad. La prueba para saber si aplica: la hija "ES UN" padre (un Perro ES UN Animal ✓).

class Animal:                       # clase PADRE (base)
    def __init__(self, nombre):
        self.nombre = nombre

    def hablar(self):
        return "..."

    def dormir(self):
        return f"{self.nombre} está durmiendo 😴"

class Perro(Animal):                # Perro HEREDA de Animal
    def hablar(self):               # SOBREESCRIBE (override) hablar
        return f"{self.nombre}: ¡Guau!"

class Gato(Animal):
    def hablar(self):
        return f"{self.nombre}: ¡Miau!"

firu = Perro("Firulais")
print(firu.hablar())    # ¡Guau!  → versión de Perro
print(firu.dormir())    # heredado de Animal sin escribirlo de nuevo
class Animal                        // clase PADRE (base)
{
    public string Nombre { get; set; }
    public Animal(string nombre) => Nombre = nombre;

    // virtual = "las hijas PUEDEN sobreescribirme"
    public virtual string Hablar() => "...";

    public string Dormir() => $"{Nombre} está durmiendo 😴";
}

class Perro : Animal                // Perro HEREDA de Animal (:)
{
    public Perro(string n) : base(n) { }   // base() llama al constructor padre
    public override string Hablar() => $"{Nombre}: ¡Guau!";
}

class Gato : Animal
{
    public Gato(string n) : base(n) { }
    public override string Hablar() => $"{Nombre}: ¡Miau!";
}

var firu = new Perro("Firulais");
Console.WriteLine(firu.Hablar());   // ¡Guau! → versión de Perro
Console.WriteLine(firu.Dormir());   // heredado de Animal

💡 Vocabulario: cambiar el comportamiento heredado se llama sobreescritura🇺🇸 Override — Redefinir en la clase hija un método heredado del padre. En C# requiere virtual/override; en Python basta con volver a definirlo. (override). En C# el padre debe marcar el método como virtual; en Python basta con redefinirlo. super() (Py) / base (C#) llaman a la versión del padre.

🎭 Pilar 4: Polimorfismo — mismo mensaje, distintas respuestas

Polimorfismo🇪🇸 Polimorfismo / 🇺🇸 Polymorphism — "Muchas formas": objetos de distintas clases responden al mismo método cada uno a su manera. Permite tratar objetos diferentes de forma uniforme. significa "muchas formas": le dices lo mismo a objetos distintos y cada uno responde a su manera. Le dices "habla" a un perro y ladra; a un gato y maúlla. Tu código no necesita preguntar qué animal es — solo confía en que todos saben hablar.

# Una sola lista con animales DISTINTOS
animales = [Perro("Firulais"), Gato("Michi"), Perro("Luna")]

for animal in animales:
    print(animal.hablar())   # cada uno responde a SU manera

# Firulais: ¡Guau!
# Michi: ¡Miau!
# Luna: ¡Guau!
# ⭐ El for NO pregunta el tipo. Eso es polimorfismo.
// Una sola lista del tipo PADRE con hijos distintos
var animales = new List<Animal>
{
    new Perro("Firulais"),
    new Gato("Michi"),
    new Perro("Luna")
};

foreach (Animal animal in animales)
    Console.WriteLine(animal.Hablar());  // cada uno a SU manera

// Firulais: ¡Guau!
// Michi: ¡Miau!
// Luna: ¡Guau!
// ⭐ El foreach NO pregunta el tipo. Eso es polimorfismo.
🚫 El anti-ejemplo que delata al principiante: if tipo == "perro": ladrar() elif tipo == "gato": maullar()... — cada animal nuevo obliga a tocar ese if. Con polimorfismo, agregar la clase Vaca no toca NADA del código existente. Ese es el superpoder.

📜 Interfaces: el contrato

Una interfaz🇪🇸 Interfaz / 🇺🇸 Interface — Contrato que lista métodos SIN implementarlos. Toda clase que la implementa se compromete a definir esos métodos. En C#: interface; en Python: ABC o Protocol. es un contrato: una lista de métodos que una clase promete tener, sin decir cómo. Como el examen de manejo: no importa si aprendiste en un Tsuru o en un Tesla, si "implementas" frenar, acelerar y estacionarte, obtienes la licencia.

from abc import ABC, abstractmethod

class Notificador(ABC):          # ABC = clase abstracta (el "contrato")
    @abstractmethod
    def enviar(self, mensaje):    # SIN implementación: solo la promesa
        ...

class NotificadorEmail(Notificador):
    def enviar(self, mensaje):
        print(f"📧 Email: {mensaje}")

class NotificadorSMS(Notificador):
    def enviar(self, mensaje):
        print(f"📱 SMS: {mensaje}")

# El código cliente solo conoce el CONTRATO, no los detalles:
def avisar_usuario(notificador, texto):
    notificador.enviar(texto)     # funciona con CUALQUIER implementación

avisar_usuario(NotificadorEmail(), "Tu pedido llegó")
avisar_usuario(NotificadorSMS(), "Tu pedido llegó")
// interface = el contrato. Por convención empiezan con I
interface INotificador
{
    void Enviar(string mensaje);   // SIN implementación: solo la promesa
}

class NotificadorEmail : INotificador
{
    public void Enviar(string mensaje)
        => Console.WriteLine($"📧 Email: {mensaje}");
}

class NotificadorSMS : INotificador
{
    public void Enviar(string mensaje)
        => Console.WriteLine($"📱 SMS: {mensaje}");
}

// El código cliente solo conoce el CONTRATO, no los detalles:
void AvisarUsuario(INotificador notificador, string texto)
    => notificador.Enviar(texto);   // CUALQUIER implementación sirve

AvisarUsuario(new NotificadorEmail(), "Tu pedido llegó");
AvisarUsuario(new NotificadorSMS(), "Tu pedido llegó");

🧱 Composición: "tiene un" vs. "es un"

La composición🇪🇸 Composición / 🇺🇸 Composition — Construir clases combinando otros objetos como piezas ("tiene un") en lugar de heredar ("es un"). Regla senior: prefiere composición sobre herencia. arma objetos combinando piezas, como LEGO. Un Coche TIENE UN motor, TIENE ruedas — no "es un motor". La regla que repiten los seniors: "prefiere composición sobre herencia", porque las jerarquías de herencia profundas se vuelven rígidas y frágiles.

class Motor:
    def encender(self):
        return "Motor rugiendo 🔥"

class Coche:
    def __init__(self):
        self.motor = Motor()      # el Coche TIENE UN motor (composición)

    def arrancar(self):
        return self.motor.encender()  # delega el trabajo a su pieza
class Motor
{
    public string Encender() => "Motor rugiendo 🔥";
}

class Coche
{
    private readonly Motor _motor = new Motor();  // TIENE UN motor

    public string Arrancar() => _motor.Encender();  // delega a su pieza
}
✅ Usa HERENCIA cuando: la relación es claramente "ES UN" y quieres polimorfismo (Perro es un Animal).
✅ Usa COMPOSICIÓN cuando: la relación es "TIENE UN" o "USA UN" (Coche tiene Motor, Reporte usa Impresora). En la duda, composición.

Módulo 6

SOLID y Patrones de Diseño

Los principios y recetas que distinguen el código profesional.

SOLID: 5 principios, 5 letras

SOLID es un acrónimo de 5 principios para escribir POO mantenible (Robert C. Martin, "Uncle Bob"). No los memorices: entiende el problema que cada uno evita.

SSingle Responsibility — Responsabilidad Única

Cada clase debe tener UNA sola razón para cambiar. Una clase Reporte que calcula datos Y los imprime Y los envía por correo hace demasiado: sepárala en 3. Analogía: en un restaurante, el chef cocina y el mesero atiende — nadie hace ambos.

OOpen/Closed — Abierto/Cerrado

Abierto a extensión, cerrado a modificación: agregar funciones nuevas sin editar el código que ya funciona. ¿Recuerdas el ejemplo de los animales? Agregar Vaca sin tocar el foreach — eso es Open/Closed en acción.

LLiskov Substitution — Sustitución de Liskov

Donde tu código espera un Animal, debe funcionar cualquier hijo sin sorpresas. Si tu clase Pinguino hereda de Ave pero truena al llamar volar(), la jerarquía está mal diseñada.

IInterface Segregation — Segregación de Interfaces

Mejor varias interfaces pequeñas y específicas que una gigante. No obligues a una clase a implementar métodos que no usa. Analogía: menú de tacos y menú de postres separados, no un menú de 40 páginas obligatorio.

DDependency Inversion — Inversión de Dependencias

Depende de abstracciones (interfaces), no de clases concretas. El ejemplo del INotificador: AvisarUsuario no sabe si es email o SMS — por eso puedes cambiar uno por otro sin tocarla. Base de la inyección de dependencias que verás en frameworks como ASP.NET.

Patrones de diseño: recetas probadas

Un patrón de diseño🇪🇸 Patrón de Diseño / 🇺🇸 Design Pattern — Solución reutilizable y documentada a un problema de diseño que aparece una y otra vez. Catalogados por la "Gang of Four" (1994). es una solución con nombre a un problema que aparece una y otra vez. Conocer los 3 más comunes te da vocabulario de equipo profesional:

🔒 Singleton

Garantiza que exista UNA sola instancia de una clase en todo el programa, con acceso global.

Uso típico: la configuración de la app, la conexión al log. Analogía: solo hay UN director en la escuela.

🏭 Factory

Centraliza la creación de objetos: pides "dame un notificador para este usuario" y la fábrica decide si construir Email o SMS.

Uso típico: crear objetos según configuración o datos. Analogía: la cocina decide cómo preparar tu platillo; tú solo lo pides.

👀 Observer

Unos objetos se "suscriben" a otro y son notificados automáticamente cuando algo cambia.

Uso típico: eventos de interfaz (clic de botón), notificaciones. Analogía: suscribirte a un canal de YouTube — te llega aviso de cada video nuevo.

⚖️ Advertencia senior: los patrones son herramientas, no trofeos. Meter 5 patrones a un programa de 100 líneas es sobre-ingeniería. Primero haz que funcione simple; aplica un patrón cuando el dolor que resuelve aparezca de verdad.
