Módulo 1

Servicios de Infraestructura TI

Los servicios invisibles que toda organización necesita para operar — y el sysadmin que los mantiene vivos.

🏢 ¿Qué son y quién los cuida?

Los servicios de infraestructura TI🇺🇸 IT Infrastructure Services — Los servicios que una organización necesita para operar: red, servidores, DNS, correo, archivos compartidos, seguridad... La "plomería" tecnológica de la empresa. son la plomería tecnológica de una empresa: nadie los nota cuando funcionan, y TODO se detiene cuando fallan. Internet, los archivos compartidos, el correo, la impresora, el "nombre de la intranet que sí abre" — todo eso son servicios que alguien configuró y mantiene: el sysadmin🇺🇸 System Administrator — Responsable de mantener la infraestructura TI: configurar servidores y servicios, dar soporte, respaldar, asegurar y planear la capacidad de los sistemas de la organización. (administrador de sistemas).

🌐 Servicios de red

DNS, DHCP, NTP, acceso remoto, VPN. El tema de esta guía: hacen que las máquinas se encuentren y se hablen.

💬 Comunicación y archivos

Correo, chat (Slack/Teams), servidores de archivos compartidos, impresión. Lo que los usuarios SÍ ven.

🛡️ Plataforma y seguridad

Bases de datos (CP6), servidores web, autenticación/directorio (Active Directory), respaldos, monitoreo (CP7).

💡 ¿Y por qué le importa a una DEV? Porque tu aplicación VIVE sobre estos servicios: si el DNS falla, tu API "no existe"; si el NTP se desvía, tus tokens expiran mal; si el DHCP se agota, nadie se conecta. Entenderlos te hace mejor desarrolladora y mucho mejor depuradora.

Sistemas operativos de servidor

Un SO de servidor🇺🇸 Server Operating System — Sistema operativo optimizado para servicios: permite más conexiones simultáneas, corre sin interfaz gráfica (headless) y soporta hardware de servidor. Ej: Windows Server, Ubuntu Server, RHEL. es un sistema operativo afinado para DAR servicios, no para usarse de escritorio:

  • 🔌 Más conexiones simultáneas: los límites de red vienen ampliados de fábrica.
  • 🖥️ Sin interfaz gráfica (headless): se administran por terminal/SSH — la GUI gasta recursos que el servicio necesita.
  • ⏱️ Pensados para no apagarse: actualizaciones y parches diseñados para minimizar reinicios.

Los que verás en el trabajo

  • 🪟 Windows Server — el estándar corporativo: Active Directory, IIS, entornos .NET (¡tu mundo C#!).
  • 🐧 Linux server — Ubuntu Server, Debian, RHEL/Rocky: domina la web, la nube y los contenedores.
  • 💡 La realidad: casi toda empresa es mixta. Saber moverte en ambos (módulo 5) es un súper diferenciador.

📦 Virtualización: muchos servidores en uno

La virtualización🇪🇸 Virtualización / 🇺🇸 Virtualization — Ejecutar varias "máquinas virtuales" (VMs) independientes sobre un mismo servidor físico, gracias a un hipervisor que reparte CPU, RAM y disco entre ellas. permite que UN servidor físico corra varias máquinas virtuales (VMs) independientes — cada una con su propio sistema operativo — gracias a un hipervisor🇺🇸 Hypervisor — El software que crea y administra las máquinas virtuales, repartiendo el hardware físico entre ellas: KVM, VMware ESXi, Microsoft Hyper-V. (KVM, VMware, Hyper-V). Analogía: en lugar de una casa por familia (un servidor físico por servicio), un edificio de departamentos: cada VM tiene su espacio privado, compartiendo la estructura.

🖥️ Servidor físico dedicado📦 Máquinas virtuales
AprovechamientoUn servicio usa 10% del hardware; el resto se desperdiciaVarias VMs exprimen el mismo hardware
RendimientoMáximo: todo el hardware para un servicioBueno, con una pequeña sobrecarga del hipervisor
MantenimientoMigrar = mover fierros físicamenteUna VM se mueve, copia o restaura como archivo
Puntos de falloSe quema el servidor = muere UN servicioSe quema el host = mueren TODAS sus VMs (por eso: redundancia, CP9)

🔗 Conexión con CP7: los contenedores (Docker) son el paso siguiente: en vez de virtualizar el hardware completo (cada VM con su SO entero), comparten el kernel y solo aíslan la app — más ligeros, pero con menos aislamiento. La nube (EC2, Azure VMs) es esencialmente virtualización rentada por hora.

Módulo 2

Acceso Remoto, FTP y NTP

Administrar servidores sin levantarte de tu silla — y por qué la hora exacta salva sistemas.

🔑 SSH: la puerta de entrada del sysadmin

SSH🇺🇸 SSH — Secure Shell (puerto 22) — Protocolo para abrir una terminal CIFRADA en una máquina remota. La herramienta #1 para administrar servidores Linux; también transfiere archivos (SCP/SFTP) y crea túneles. (Secure Shell, puerto 22) te da una terminal cifrada dentro de un servidor remoto: todo lo que harías sentada frente a él, desde tu casa. Su equivalente gráfico en el mundo Windows es RDP (Remote Desktop, puerto 3389), que transmite el escritorio completo.

# Conectarte a un servidor remoto
ssh nayeli@servidor01.empresa.com

# Mejor práctica: llaves SSH en vez de contraseñas
ssh-keygen -t ed25519              # genera tu par de llaves (una vez)
ssh-copy-id nayeli@servidor01     # instala tu llave pública en el servidor
# A partir de aquí: entras sin contraseña, y puedes DESACTIVAR
# el login por contraseña (adiós fuerza bruta — ¿recuerdas CP8?)

# Copiar archivos por el mismo canal cifrado
scp reporte.pdf nayeli@servidor01:/home/nayeli/
# Windows moderno también trae cliente OpenSSH:
ssh nayeli@servidor01.empresa.com

# Para servidores WINDOWS, lo tradicional es RDP (escritorio remoto):
mstsc /v:servidor01.empresa.com    # abre el cliente de Escritorio Remoto

# Y para administrar por consola (el "SSH de Windows"):
Enter-PSSession -ComputerName servidor01   # PowerShell Remoting (WinRM)
# Ahora cada comando corre EN el servidor remoto

🛡️ Nota de seguridad (CP8 aplicado): SSH con llaves > SSH con contraseña; nunca expongas RDP directo a internet (es de los puertos más atacados del mundo) — siempre detrás de una VPN.

📁 La familia FTP: tres primos muy distintos

ProtocoloPuerto¿Cifrado?Cuándo lo verás
FTP (File Transfer Protocol)21❌ No — TODO viaja en texto plano, hasta la contraseñaSistemas legados y hostings viejos. En 2026: evítalo
SFTP (SSH File Transfer)22✅ Sí — viaja dentro del túnel SSHEl estándar actual para transferir archivos a servidores. Clientes: FileZilla, WinSCP
TFTP (Trivial FTP)69❌ No — y ni siquiera pide usuarioRedes internas: arranque de equipos por red (PXE) y configuración de routers/switches

🧠 Truco de examen: la T de TFTP es de "Trivial" — tan simple que no autentica ni cifra. Solo tiene sentido en redes internas controladas, para archivos que no son secretos (imágenes de arranque, configs de switches).

🕐 NTP: el servicio más aburrido... hasta que falla

NTP🇺🇸 NTP — Network Time Protocol (puerto 123) — Sincroniza los relojes de todas las máquinas de la red contra servidores de tiempo de referencia. Milisegundos de precisión a través de internet. (Network Time Protocol, puerto 123) mantiene los relojes de TODAS las máquinas sincronizados contra servidores de referencia. Suena trivial... hasta que ves lo que se rompe con relojes desviados unos minutos:

🔐 La autenticación muere

Kerberos (el corazón de Active Directory) rechaza tokens con más de 5 minutos de desfase: nadie puede iniciar sesión. Los JWT (CP3) expiran "antes de tiempo" o viven de más.

📜 Los logs mienten

¿Cómo reconstruyes un incidente (CP7) si el servidor A dice 10:03 y el B dice 10:07 para el MISMO instante? El orden de los eventos se vuelve ficción.

🔒 HTTPS sospecha

Los certificados TLS (CP8) tienen fechas de validez: un reloj muy desviado hace que el navegador rechace certificados perfectamente válidos.

En la práctica: los servidores se apuntan a pools públicos (pool.ntp.org) o al controlador de dominio, y el sysadmin solo verifica que el servicio esté sano (timedatectl en Linux, w32tm /query /status en Windows).

Módulo 3

DNS a Fondo

La agenda telefónica de internet: de nombre a dirección IP.

📖 El viaje de una consulta DNS

Las máquinas se hablan por direcciones IP (142.250.65.78); los humanos recordamos nombres (google.com). El DNS🇺🇸 DNS — Domain Name System (puerto 53) — El sistema jerárquico distribuido que traduce nombres de dominio a direcciones IP. Sin él, internet sería memorizar números. (puerto 53) es el traductor. Cuando escribes miempresa.com, la resolución sigue una cadena de "¿tú sabes?":

1. Caché local de tu máquina — ¿ya lo busqué hace poco? (más /etc/hosts)

2. Resolver recursivo — el DNS de tu red o proveedor (o 8.8.8.8 / 1.1.1.1): busca por ti

3. Servidores raíz — "no sé miempresa.com, pero los .com los lleva aquel" →

4. Servidores TLD (.com) — "pregúntale a los servidores autoritativos del dominio" →

5. Servidor autoritativo — "miempresa.com es 203.0.113.10" ✅ (y todos lo cachean con su TTL)

El TTL de cada registro dice cuánto tiempo puede cachearse la respuesta — el mismo concepto del caché de CP5. Por eso los cambios de DNS "tardan en propagar": el mundo espera a que expiren los cachés.

Los tipos de registro que debes reconocer

RegistroTraduce...Ejemplo
ANombre → IPv4miempresa.com → 203.0.113.10
AAAANombre → IPv6 (la "cuádruple A")miempresa.com → 2001:db8::10
CNAMEAlias → otro nombre (el "también conocido como")www.miempresa.com → miempresa.com
MX¿Quién recibe el CORREO del dominio?miempresa.com → mail.google.com (prioridad 10)
TXTTexto libre: verificaciones y anti-spam (SPF/DKIM)"v=spf1 include:_spf.google.com ~all"
NS¿Qué servidores son los autoritativos del dominio?miempresa.com → ns1.cloudflare.com
PTREl inverso: IP → nombre (reverse DNS)203.0.113.10 → miempresa.com

🌍 DNS para servidores web (público)

Compras el dominio en un registrar (Namecheap, GoDaddy), apuntas sus NS a tu proveedor de DNS (Cloudflare, Route 53), y creas los registros A/CNAME hacia la IP de tu servidor o balanceador (CP7).

Es el mapa que conecta "miapp.com" con el backend que construiste en CP3-CP7. Truco pro: TTL bajo (300s) ANTES de una migración para poder cambiar rápido.

🏠 DNS para redes internas

Dentro de la empresa hay OTRO DNS que internet no ve: impresora-piso2.empresa.local, servidor-nomina.interno. Nadie memoriza las IPs privadas de 500 equipos.

En el mundo Windows lo lleva el controlador de dominio (Active Directory); en redes pequeñas, un dnsmasq (módulo 6). Los nombres internos NUNCA deben resolverse desde fuera.

Módulo 4

DHCP

Cómo tu laptop obtiene una IP sin que nadie la configure.

🎫 El problema que resuelve

Cada dispositivo en la red necesita: una IP única, la máscara de red, la puerta de enlace (gateway) y los servidores DNS. ¿Configurar eso A MANO en 500 laptops, teléfonos y visitantes? Imposible de mantener (y garantía de IPs duplicadas). El DHCP🇺🇸 DHCP — Dynamic Host Configuration Protocol (puertos 67/68) — Asigna automáticamente la configuración de red (IP, máscara, gateway, DNS) a cada dispositivo que se conecta, en préstamo (lease) temporal. lo automatiza: te conectas, y en segundos tienes todo. Analogía: el hotel que al hacer check-in te asigna habitación disponible, te da la llave y el mapa — por un número de noches limitado.

El baile de 4 pasos: DORA

D

Discover

Tu equipo grita a toda la red: "¿hay algún servidor DHCP por aquí?" (broadcast)

O

Offer

El servidor responde: "te ofrezco la 192.168.1.47, con este gateway y estos DNS"

R

Request

Tu equipo: "¡acepto esa oferta!" (por si varios servidores ofrecieron)

A

Acknowledge

El servidor confirma: "es tuya por 24 horas" (el lease)

El lease🇺🇸 DHCP Lease — El "préstamo" de la IP por tiempo limitado (horas o días). El cliente lo renueva a la mitad del plazo; si no, la IP regresa al pool para otro dispositivo. es un préstamo: a la mitad del plazo, el cliente lo renueva en silencio. Si el equipo se va (visitante del café), su IP regresa al pool para el siguiente.

Lo que configura el sysadmin

📏 El rango (scope/pool)

Qué IPs puede repartir: ej. de la .100 a la .200. Las de abajo (.1–.99) se reservan para asignación fija: routers, servidores, impresoras.

📌 Reservas por MAC

"A la impresora con MAC AA:BB:CC... dale SIEMPRE la .50". Lo mejor de ambos mundos: IP fija, pero administrada centralmente en el DHCP, no equipo por equipo.

🎁 Las opciones que regala

Junto con la IP entrega: gateway (por dónde salir a internet), servidores DNS (módulo 3) y máscara. Por eso DHCP mal configurado = "tengo red pero no internet".

🔗 DHCP + DNS, el dúo dinámico: en redes bien montadas, cuando el DHCP presta una IP también registra el nombre del equipo en el DNS interno (DNS dinámico): "laptop-nayeli" se vuelve resoluble al instante. Y el clásico del troubleshooting: si el pool se AGOTA (más dispositivos que IPs en el rango), los nuevos simplemente "no tienen red" — revisar el scope es de las primeras cosas que un sysadmin verifica.

Módulo 5

Gestionar Servicios en Linux y Windows

Arrancar, detener, habilitar y configurar los programas que corren solos.

👻 ¿Qué es un servicio (daemon)?

Un servicio🇪🇸 Servicio / 🇺🇸 Service (daemon) — Programa que corre en segundo plano sin interfaz, normalmente desde el arranque: el servidor web, la base de datos, el DNS. En Linux se les llama daemons; en Windows, services. es un programa que corre en segundo plano, sin ventana, desde el arranque: el servidor web, la base de datos, el SSH, el DNS. En Linux se llaman daemons (de ahí la "d" final en sshd, systemd); en Windows, services. Todo lo de esta guía — DNS, DHCP, NTP — vive como servicio en alguna máquina. Los verbos del oficio:

# ¿Cómo está el servicio? (el comando que más usarás)
sudo systemctl status nginx

# Arrancar / detener / reiniciar
sudo systemctl start nginx
sudo systemctl stop nginx
sudo systemctl restart nginx     # corta y vuelve a arrancar
sudo systemctl reload nginx      # relee la config SIN cortar conexiones ✨

# ¿Arranca solo al encender la máquina?
sudo systemctl enable nginx      # sí, desde el próximo arranque
sudo systemctl disable nginx     # no
# OJO: enable NO lo arranca ahora; start NO lo habilita al arranque.
# Son independientes: enable --now hace ambos.

# Ver sus logs (¡la mina de oro del troubleshooting!)
journalctl -u nginx -f           # -f = en vivo, como una cola
# ¿Cómo está el servicio?
Get-Service -Name W32Time        # o spooler, WinRM, MSSQLSERVER...

# Arrancar / detener / reiniciar
Start-Service W32Time
Stop-Service W32Time
Restart-Service W32Time

# ¿Arranca solo al encender? (tipo de inicio)
Set-Service W32Time -StartupType Automatic   # o Manual / Disabled

# Listar todos los que están corriendo
Get-Service | Where-Object { $_.Status -eq "Running" }

# La versión gráfica: services.msc (la consola de Servicios)
# Y los logs viven en el Visor de Eventos (eventvwr) → Windows Logs

⚙️ Configurar servicios: el ciclo sagrado

En Linux, la configuración vive en archivos de texto bajo /etc/ (ej. /etc/nginx/nginx.conf, /etc/ssh/sshd_config). En Windows, en la app del servicio, el Registro o archivos de config. El ritual profesional es SIEMPRE el mismo:

  1. 1Respalda el archivo antes de tocarlo: sudo cp sshd_config sshd_config.bak. Treinta segundos que un día te salvarán la noche.
  2. 2Edita el cambio (nano/vim, o el editor que sea).
  3. 3Valida la sintaxis SIN reiniciar si el servicio lo permite: nginx -t, sshd -t, named-checkconf. Detecta el typo ANTES de tumbar el servicio.
  4. 4Aplica con reload (si existe) o restart, y verifica: status + logs + probar la función.
⚠️ La trampa clásica del SSH: si editas sshd_config en un servidor REMOTO y reinicias con un error de sintaxis... te quedas fuera del servidor. Por eso: valida con sshd -t, y mantén una segunda sesión SSH abierta hasta confirmar que la nueva config deja entrar.

Módulo 6

Troubleshooting y Dnsmasq

"No abre la página": el diagnóstico paso a paso, y tu propio DNS/DHCP casero.

🕵️ "No resuelve el hostname": el diagnóstico en capas

El reporte llega como "no abre tal página / no encuentra tal servidor". El error del novato: adivinar. El método pro: aislar la capa que falla, de abajo hacia arriba — exactamente el debugging sistemático de CP1, aplicado a redes:

# PASO 1 — ¿Tengo red siquiera? Ping a una IP directa (sin DNS de por medio)
ping 8.8.8.8
#   ✅ responde → hay red; el problema es de NOMBRES (sigue al paso 2)
#   ❌ no responde → problema de red/gateway/DHCP, no de DNS

# PASO 2 — ¿Resuelve el nombre? Pregunta directa al DNS
nslookup miempresa.com           # ¿qué IP devuelve? ¿quién respondió?
dig miempresa.com                # la versión detallada (status, TTL, servidor)

# PASO 3 — ¿Y con OTRO servidor DNS? (aísla si el problema es TU dns)
nslookup miempresa.com 8.8.8.8
#   ✅ con 8.8.8.8 sí resuelve → tu DNS local es el culpable

# PASO 4 — Revisar la config local
cat /etc/hosts                   # ¿alguien "hardcodeó" el nombre aquí?
cat /etc/resolv.conf             # ¿qué DNS está usando la máquina?
sudo resolvectl flush-caches     # limpiar el caché DNS local
# PASO 1 — ¿Tengo red siquiera? Ping a una IP directa (sin DNS de por medio)
ping 8.8.8.8
#   ✅ responde → hay red; el problema es de NOMBRES (sigue al paso 2)
#   ❌ no responde → problema de red/gateway/DHCP, no de DNS

# PASO 2 — ¿Resuelve el nombre? Pregunta directa al DNS
nslookup miempresa.com           # ¿qué IP devuelve? ¿quién respondió?
Resolve-DnsName miempresa.com    # la versión PowerShell, más detallada

# PASO 3 — ¿Y con OTRO servidor DNS? (aísla si el problema es TU dns)
nslookup miempresa.com 8.8.8.8
#   ✅ con 8.8.8.8 sí resuelve → tu DNS local es el culpable

# PASO 4 — Revisar la config local
type C:\Windows\System32\drivers\etc\hosts   # ¿nombre hardcodeado?
ipconfig /all                    # ¿qué DNS está usando la máquina?
ipconfig /flushdns               # limpiar el caché DNS local

🧠 La lógica: cada paso descarta una capa. ¿Ping a IP funciona pero el nombre no? → DNS. ¿Otro DNS sí resuelve? → tu servidor DNS. ¿El archivo hosts tiene una entrada vieja? → ahí está el fantasma (es la causa #1 de "solo a MÍ no me abre").

🧰 Dnsmasq: DNS + DHCP en un paquetito

Dnsmasq🇺🇸 dnsmasq — Servidor ligero que combina DNS (con caché y nombres locales) y DHCP en un solo servicio. Ideal para redes pequeñas, laboratorios y routers domésticos — muchos lo traen integrado. es un servidor LIGERO que hace de DNS y DHCP a la vez — perfecto para redes pequeñas, laboratorios y para practicar todo lo de esta guía en tu propia máquina. De hecho, tu router de casa probablemente corre dnsmasq por dentro:

# /etc/dnsmasq.conf — un DNS + DHCP completo en 8 líneas

# --- DNS ---
server=8.8.8.8                       # a quién preguntar lo que no sepa
address=/servidor-nas.local/192.168.1.10   # nombre interno → IP
address=/impresora.local/192.168.1.20
cache-size=1000                      # caché de respuestas (¡CP5!)

# --- DHCP ---
dhcp-range=192.168.1.100,192.168.1.200,24h   # el pool y el lease
dhcp-option=option:router,192.168.1.1        # el gateway que regala
dhcp-host=AA:BB:CC:DD:EE:FF,192.168.1.50     # reserva por MAC

# Aplicar: sudo systemctl restart dnsmasq   (¡el ciclo del módulo 5!)
# Probar:  dig servidor-nas.local @127.0.0.1

🎓 Ejercicio recomendado: instala dnsmasq en una VM o Raspberry Pi y monta tu propio DNS interno con nombres para tus dispositivos. En 30 minutos habrás tocado con las manos TODO lo de esta guía: servicios, config, DNS, DHCP y troubleshooting.
