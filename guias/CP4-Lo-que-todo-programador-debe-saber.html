Módulo 1

Git y Control de Versiones

La máquina del tiempo (y el trabajo en equipo) del código.

🎮 La analogía del videojuego

¿"proyecto_final_v2_AHORA_SI_bueno.zip"? El control de versiones🇪🇸 Control de Versiones / 🇺🇸 Version Control — Sistema que registra el historial de cambios de los archivos, permitiendo volver a cualquier punto anterior y trabajar en equipo sin pisarse. resuelve eso profesionalmente. Git🇺🇸 Git — El sistema de control de versiones más usado del mundo (Linus Torvalds, 2005). Distribuido: cada quien tiene copia completa del historial. es como los puntos de guardado de un videojuego: cada commit🇺🇸 Commit — "Foto" del estado del proyecto en un momento dado, con mensaje descriptivo. La unidad básica del historial de Git. es un save point con descripción, y puedes volver a cualquiera si algo sale mal. Además, varias personas juegan la misma partida sin borrarse el progreso.

📸 Commit

Una "foto" de tu proyecto con mensaje: "agrega validación de correo". El historial es la cadena de fotos.

🌿 Branch (rama)

Una línea de tiempo paralela para trabajar sin afectar la principal (main). Terminas tu función, y la unes con un merge.

☁️ GitHub

La copia remota compartida del repositorio + herramientas de equipo (pull requests, issues). Git es la herramienta; GitHub, el servicio en la nube.

El flujo básico del día a día

# 1. Clonar (una sola vez): descargar el repositorio
git clone https://github.com/equipo/proyecto.git

# 2. Crear una rama para tu tarea
git checkout -b feature/validar-correo

# ... editas archivos ...

# 3. Revisar qué cambió
git status

# 4. Preparar los cambios (área de staging)
git add .

# 5. Guardar la "foto" con mensaje descriptivo
git commit -m "Agrega validación de formato de correo"

# 6. Subir tu rama al remoto (GitHub)
git push origin feature/validar-correo

# 7. Traer los cambios de los demás
git pull

📥 Pull Request (PR): la revisión entre colegas

Cuando tu rama está lista, abres un Pull Request: una solicitud de "quiero unir mis cambios a main". El equipo revisa tu código, comenta, pides ajustes... y al aprobarse, se hace el merge. Es el mecanismo #1 de calidad y aprendizaje en equipos profesionales.

⚔️ Conflictos de merge (no entres en pánico)

Si dos personas cambian la misma línea, Git no adivina quién gana: marca el conflicto y te pide decidir. Ves ambas versiones entre <<<< y >>>>, eliges (o combinas), y haces commit. Molesto pero normal: le pasa a todos, todas las semanas.

💼 Tu portafolio vive aquí: para reclutadores, tu perfil de GitHub ES tu currículum técnico. Sube tus proyectos de práctica con buenos README y commits descriptivos — demuestras Git y tus proyectos al mismo tiempo.

Módulo 2

Bases de Datos

Donde los datos viven cuando el programa se apaga.

🗄️ ¿Por qué necesito una base de datos?

Las variables de CP1 viven en la memoria RAM: al cerrar el programa, se pierden. Una base de datos🇪🇸 Base de Datos / 🇺🇸 Database — Sistema para almacenar, organizar y consultar datos de forma persistente, eficiente y segura, incluso con millones de registros y muchos usuarios a la vez. guarda los datos de forma persistente (sobreviven al apagón), permite buscarlos eficientemente entre millones, y coordina que muchos usuarios lean y escriban a la vez sin corromperse.

📊 Relacionales (SQL)

Datos en tablas con filas y columnas, conectadas entre sí (por eso "relacionales"). Estructura estricta definida de antemano.

SQL Server, MySQL, PostgreSQL, Oracle, SQLite

📦 NoSQL

Datos en documentos (tipo JSON), pares clave-valor u otros modelos flexibles. La estructura puede variar entre registros.

MongoDB, Redis, DynamoDB, Cassandra

🧭 Regla simple: datos estructurados con relaciones claras (ventas, inventarios, usuarios) → SQL. Datos flexibles/variables o caché de alta velocidad → NoSQL. La mayoría de las empresas usan ambas.

SQL: las 4 consultas del CRUD

SQL🇺🇸 SQL — Structured Query Language — Lenguaje estándar para consultar y manipular bases de datos relacionales. Creado por IBM en los 70s y sigue siendo el estándar. es el lenguaje para hablar con bases relacionales. ¿Recuerdas el CRUD de las APIs (CP3)? Aquí está su versión en SQL sobre una tabla Productos:

-- CREATE: insertar un registro nuevo
INSERT INTO Productos (nombre, precio, stock)
VALUES ('Laptop Dell XPS', 24999.90, 15);

-- READ: consultar (la consulta más usada del planeta)
SELECT nombre, precio FROM Productos
WHERE precio < 30000          -- filtro
ORDER BY precio DESC;         -- ordenar de mayor a menor

-- UPDATE: modificar registros existentes
UPDATE Productos SET stock = 14
WHERE id = 42;                -- ⚠️ SIN where, actualizas TODA la tabla

-- DELETE: eliminar registros
DELETE FROM Productos WHERE id = 42;   -- ⚠️ mismo peligro sin WHERE
🚨 La cicatriz de todo programador: ejecutar un UPDATE o DELETE sin WHERE y modificar/borrar la tabla completa. Costumbre profesional: escribe primero el SELECT con tu WHERE, verifica qué devuelve, y solo entonces conviértelo en UPDATE/DELETE.

Conceptos clave de las bases relacionales

🔑 Llave primaria (PK)

El identificador único de cada fila (el id). Como la CURP: no puede repetirse ni faltar.

🔗 Llave foránea (FK)

Columna que apunta a la PK de otra tabla: Pedidos.cliente_id → Clientes.id. Así se "relacionan" las tablas.

🤝 JOIN

Combinar tablas en una consulta: "dame cada pedido CON el nombre de su cliente". El pan de cada día en reportes.

🔌 ¿Y cómo se conecta esto con mi código? Desde Python/C# ejecutas SQL mediante librerías, o usas un ORM (Object-Relational Mapper) que traduce objetos ↔ tablas automáticamente: Entity Framework en C#, SQLAlchemy / Django ORM en Python. Con un ORM escribes db.Productos.Where(p => p.Precio < 30000) y él genera el SQL. Aun así: entender SQL es irremplazable para depurar y optimizar.

Módulo 3

Testing y Debugging

Encontrar los errores antes que tus usuarios.

🧪 ¿Por qué escribir pruebas?

Una prueba automatizada🇪🇸 Prueba Automatizada / 🇺🇸 Automated Test — Código que verifica que otro código funciona como se espera. Se ejecutan en segundos, cuantas veces quieras. es código que verifica tu código. La magia no está en probarlo HOY (eso lo haces a mano), sino en volver a probarlo gratis para siempre: cambias algo en 6 meses, corres las pruebas, y en segundos sabes si rompiste algo. Es la red de seguridad del trapecista: te permite hacer cambios audaces sin miedo.

🔬 Unitarias

Prueban UNA función/clase aislada. Rápidas y abundantes. La base de la pirámide.

🔗 De integración

Prueban que varias piezas funcionen JUNTAS: tu código + la base de datos + la API.

🌐 End-to-End (E2E)

Simulan a un usuario real usando la app completa. Valiosas pero lentas: pocas y las más críticas.

Tu primera prueba unitaria

Probemos la función calcular_precio_final de CP1. El patrón universal es AAA: Arrange (preparar), Act (ejecutar), Assert (verificar):

# archivo: test_precios.py  →  se corre con: pytest
from precios import calcular_precio_final

def test_precio_con_impuesto_default():
    # Arrange (preparar) + Act (ejecutar)
    resultado = calcular_precio_final(100)
    # Assert (verificar): si no se cumple, la prueba FALLA
    assert resultado == 116.0

def test_precio_con_impuesto_personalizado():
    assert calcular_precio_final(100, 0.08) == 108.0

def test_precio_cero():          # ¡no olvides los casos límite!
    assert calcular_precio_final(0) == 0.0
// archivo: PreciosTests.cs  →  se corre con: dotnet test
using Xunit;

public class PreciosTests
{
    [Fact]   // marca el método como prueba
    public void PrecioConImpuestoDefault()
    {
        // Arrange + Act
        var resultado = Precios.CalcularPrecioFinal(100);
        // Assert (verificar): si no se cumple, la prueba FALLA
        Assert.Equal(116, resultado);
    }

    [Theory]  // prueba parametrizada: varios casos de una vez
    [InlineData(100, 0.08, 108)]
    [InlineData(0, 0.16, 0)]      // ¡no olvides los casos límite!
    public void PrecioConImpuestoPersonalizado(decimal precio, decimal imp, decimal esperado)
    {
        Assert.Equal(esperado, Precios.CalcularPrecioFinal(precio, imp));
    }
}

🔄 TDD en 20 segundos

El Test-Driven Development invierte el orden: 1) escribe la prueba (falla, rojo), 2) escribe el código mínimo para pasarla (verde), 3) mejora el código sin romperla (refactor). No es obligatorio en todos lados, pero debes saber qué significa.

🐛 Debugging sistemático (repaso pro de CP1)

  1. 1. Reproduce el error de forma consistente.
  2. 2. Lee el mensaje/stack trace completo (en serio, léelo).
  3. 3. Aísla con breakpoints o prints dónde se tuerce el dato.
  4. 4. Corrige la causa, no el síntoma.
  5. 5. Escribe una prueba que cubra ese caso: ese bug no vuelve jamás.

Módulo 4

Clean Code

El código se escribe una vez y se lee cientos de veces.

📖 Mismo programa, dos mundos

Ambos códigos hacen exactamente lo mismo. ¿Cuál quisieras heredar de un compañero que ya no está en la empresa?

# ❌ ANTES: funciona, pero nadie sabe qué hace
def f(x, y):
    z = x * y
    if z > 5000: z = z * 0.9
    return z * 1.16

# ✅ DESPUÉS: se explica solo, sin un solo comentario
DESCUENTO_MAYOREO = 0.10
UMBRAL_MAYOREO = 5000
IVA = 0.16

def calcular_total_con_iva(precio_unitario, cantidad):
    subtotal = precio_unitario * cantidad
    if subtotal > UMBRAL_MAYOREO:
        subtotal *= (1 - DESCUENTO_MAYOREO)
    return subtotal * (1 + IVA)
// ❌ ANTES: funciona, pero nadie sabe qué hace
double F(double x, int y)
{
    var z = x * y;
    if (z > 5000) z *= 0.9;
    return z * 1.16;
}

// ✅ DESPUÉS: se explica solo, sin un solo comentario
const decimal DescuentoMayoreo = 0.10m;
const decimal UmbralMayoreo = 5000m;
const decimal Iva = 0.16m;

decimal CalcularTotalConIva(decimal precioUnitario, int cantidad)
{
    var subtotal = precioUnitario * cantidad;
    if (subtotal > UmbralMayoreo)
        subtotal *= (1 - DescuentoMayoreo);
    return subtotal * (1 + Iva);
}

Los números sueltos como 5000 y 0.9 se llaman "números mágicos" — nadie sabe qué significan. Darles nombre es la mejora más barata y poderosa que existe.

Las reglas de oro

🏷️ Nombres que cuentan la historia

Variables = sustantivos (saldoDisponible); funciones = verbos (enviar_recibo()); booleanos = pregunta (esValido, tieneStock). Si necesitas un comentario para explicar el nombre, el nombre está mal.

✂️ Funciones cortas, una responsabilidad

Si una función se llama validar_y_guardar_y_notificar()... son tres funciones. Si no cabe en una pantalla, casi seguro hace demasiado.

💬 Comentarios: el PORQUÉ, no el QUÉ

❌ # suma 1 a i (eso ya lo dice el código). ✅ # el API del banco redondea hacia abajo, compensamos aquí (contexto que el código NO puede decir).

🔤 Siglas que debes dominar

DRY (no te repitas: extrae funciones), KISS (Keep It Simple: lo simple gana), YAGNI (You Aren't Gonna Need It: no programes "por si acaso" funcionalidad que nadie pidió).

Convenciones de nombres: camelCase, PascalCase y compañía

Cada estilo de escritura tiene nombre propio, y cada lenguaje tiene reglas de etiqueta sobre cuándo usar cada uno. Seguirlas hace que tu código "se vea nativo" — no seguirlas delata al recién llegado en la primera línea:

🔍 ¿Ya lo habías notado? Todos los ejemplos de estas guías siguen estas reglas: en Python escribimos calcular_precio_final y en C# CalcularPrecioFinal — el MISMO método, "vestido" según el lenguaje. La interfaz INotificador de CP2 lleva su I porque así lo dicta la convención de C#.
📏 Las 3 reglas de oro: 1) Consistencia ante todo — peor que elegir "mal" es mezclar estilos en el mismo proyecto. 2) Sigue la convención del lenguaje, no tu gusto personal (el código es del equipo). 3) Si el proyecto ya existe, imita lo que hay — aunque no sea tu estilo favorito.
👀 Code review: en equipos profesionales, nadie une código a main sin que otro lo revise (¿recuerdas el Pull Request del módulo 1?). No es desconfianza: es cómo se detectan bugs temprano y cómo se aprende más rápido. Recibir comentarios en tu código es lo normal — no es personal, es el proceso.

Módulo 5

Rendimiento y Big-O

¿Qué le pasa a tu programa cuando los datos crecen 1000x?

📈 La pregunta correcta

La notación Big-O🇺🇸 Big-O Notation — Forma de describir cómo crece el tiempo (o memoria) de un algoritmo cuando crecen los datos de entrada. No mide segundos: mide la FORMA del crecimiento. no mide segundos: responde "si los datos se multiplican por 1000, ¿el tiempo se multiplica por cuánto?". Tu código puede volar con 100 registros de prueba y morir con el millón de producción — Big-O te lo advierte ANTES.

NotaciónNombreAnalogíaEjemplo típico
O(1)ConstanteAbrir tu casillero: sabes el número, da igual cuántos hayaBuscar por clave en un diccionario
O(log n)LogarítmicaBuscar en el diccionario de papel: abres a la mitad, descartas media, repitesBúsqueda binaria en lista ordenada
O(n)LinealLeer una lista nombre por nombre hasta encontrar el tuyoRecorrer una lista con un for
O(n²)CuadráticaQue cada invitado de la fiesta salude a TODOS los demásBucle anidado sobre la misma lista

El mismo problema, dos velocidades

¿Hay algún valor duplicado en una lista? Observa cómo el diccionario/set convierte O(n²) en O(n):

# ❌ O(n²): por CADA elemento, recorre TODA la lista otra vez
def hay_duplicados_lento(numeros):
    for i in range(len(numeros)):
        for j in range(i + 1, len(numeros)):
            if numeros[i] == numeros[j]:
                return True
    return False
# 10,000 elementos → ~50 MILLONES de comparaciones 🐌

# ✅ O(n): un solo recorrido, usando un set (búsqueda O(1))
def hay_duplicados_rapido(numeros):
    vistos = set()
    for n in numeros:
        if n in vistos:      # preguntar al set es casi instantáneo
            return True
        vistos.add(n)
    return False
# 10,000 elementos → 10,000 pasos 🚀
// ❌ O(n²): por CADA elemento, recorre TODA la lista otra vez
bool HayDuplicadosLento(List<int> numeros)
{
    for (int i = 0; i < numeros.Count; i++)
        for (int j = i + 1; j < numeros.Count; j++)
            if (numeros[i] == numeros[j])
                return true;
    return false;
}
// 10,000 elementos → ~50 MILLONES de comparaciones 🐌

// ✅ O(n): un solo recorrido, usando un HashSet (búsqueda O(1))
bool HayDuplicadosRapido(List<int> numeros)
{
    var vistos = new HashSet<int>();
    foreach (var n in numeros)
    {
        if (vistos.Contains(n))   // casi instantáneo
            return true;
        vistos.Add(n);
    }
    return false;
}
// 10,000 elementos → 10,000 pasos 🚀
🧠 Lo que un senior hace con esto en la práctica: 1) Sospecha de los bucles anidados sobre datos grandes. 2) Recuerda que buscar en diccionario/set es O(1) y en lista es O(n) — por eso elegir la estructura correcta (CP1) ES optimizar. 3) No optimiza a ciegas: primero mide, luego mejora lo que de verdad es lento. "La optimización prematura es la raíz de todos los males" — Donald Knuth.

Módulo 6

Arquitectura y Despliegue

El mapa completo: del código en tu máquina a la app en producción.

🗺️ Las 3 capas de casi toda aplicación

🎨 Frontend

Lo que el usuario VE y toca: la página web (HTML/CSS/JavaScript), la app móvil. El "comedor" del restaurante.

⚙️ Backend

La lógica del negocio que corre en el servidor (Python, C#...). Valida, calcula, decide. La "cocina". Expone su funcionalidad como... ¡una API (CP3)!

🗄️ Base de datos

Donde los datos persisten (módulo 2). La "bodega". Solo el backend habla con ella, nunca el frontend directo.

🔁 El flujo completo ya lo conoces de las otras guías: el frontend hace una petición HTTP → la API del backend la procesa (con la POO de CP2) → consulta la base de datos con SQL → devuelve JSON → el frontend lo pinta. Las 4 guías de este curso son este diagrama.

Monolito vs. Microservicios

🏢 Monolito

TODA la aplicación en un solo programa desplegado junto. Como una casa: todo bajo un techo.

  • ✅ Simple de desarrollar, probar y desplegar
  • ✅ Ideal para equipos chicos y proyectos nuevos
  • ❌ Al crecer, todo se despliega junto y un error tira todo

🏘️ Microservicios

La app dividida en servicios pequeños e independientes (pagos, inventario, usuarios...) que se comunican por APIs. Como una plaza comercial: cada local opera solo.

  • ✅ Cada servicio se despliega y escala por separado
  • ✅ Equipos independientes por servicio
  • ❌ MUCHA más complejidad operativa (red, monitoreo, versiones)
⚖️ Respuesta senior en entrevista: "empieza con un monolito bien organizado; migra a microservicios cuando el dolor real (equipos grandes, escalar partes distintas) lo justifique". Los microservicios no son "lo moderno": son una solución cara a problemas de escala que quizá no tienes.

La nube y el camino a producción

☁️ La nube en corto

Rentar computadoras y servicios de AWS, Azure o Google Cloud en lugar de comprar servidores. Pagas por uso, creces en minutos.

  • IaaS: te rentan la máquina virtual pelona (tú instalas todo). Rentar el terreno.
  • PaaS: te rentan la plataforma lista para subir tu código. Rentar el local equipado.
  • SaaS: software terminado que solo usas (Gmail, Office 365). Comer en el restaurante.

🚀 Entornos y CI/CD

El código pasa por ambientes: desarrollo (tu máquina) → staging/QA (réplica para probar) → producción (los usuarios reales).

CI/CD🇺🇸 CI/CD — Continuous Integration / Continuous Deployment — Automatización que compila, prueba y despliega el código automáticamente en cada cambio subido al repositorio. automatiza el viaje: cada push a Git dispara una línea de ensamblaje que compila, corre TODAS las pruebas (módulo 3) y, si pasan, despliega solo. Sin "subir archivos por FTP a mano un viernes".

🎓 El mapa final: cómo se conecta TODO lo que aprendiste

• Escribes lógica con fundamentos (CP1) organizada en clases con POO (CP2)...

• ...la expones como API (CP3) que guarda en una base de datos (CP4-2)...

• ...versionada con Git (CP4-1), protegida por pruebas (CP4-3), legible gracias al clean code (CP4-4)...

• ...eficiente gracias a Big-O (CP4-5) y desplegada a la nube con CI/CD (CP4-6). Ese es el ciclo de vida completo del software profesional. 🎉
